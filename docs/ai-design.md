## 3. 최선의 수를 어떻게 판단할 것인가

### 3-1. 데미지 비교만으로는 안 되는 이유

기술 4개의 데미지를 비교하면 변화기는 전부 0이라 영원히 안 뽑힌다.
그런데 실전에서는 칼춤이 정답인 경우가 훨씬 많다.

원인은 **"이번 턴의 이득"만 보기 때문**이다. 칼춤은 이번 턴 이득이 0이고 다음 턴부터 이득이 난다.

### 3-2. 해결 — 모든 수를 같은 자로 잰다

비교하려면 단위가 같아야 한다. 그 단위는 결국 하나다.

> **"이 수를 두면 내가 이길 확률이 얼마나 올라가는가"**

직접 계산할 수 없으니, **몇 턴 뒤의 상황에 점수를 매기고 거슬러 올라오는** 방식을 쓴다.
체스·바둑 AI와 같은 원리다.

### 3-3. 기술 종류별 환산

| 종류 | 어떻게 점수로 바꾸나 |
|---|---|
| 공격기 | 준 데미지 |
| 랭크업기 | 이번 턴 0, 다음 턴부터 데미지 배수. 그 사이 맞을 데미지가 비용 |
| 회복기 | 회복한 HP = 마이너스 데미지 |
| 상태이상기 | 앞으로 **받을** 데미지가 줄어드는 양 (화상=물리 반감, 마비=스피드 절반) |
| 압정·스텔스록 | 상대가 교체할 때마다 누적 → 남은 턴이 길수록 가치가 큼 |
| 교체 | 이번 턴 공짜로 맞아주는 비용 vs 상성 우위 이득 |

칼춤이 좋은지는 **"2턴 뒤에 내가 더 유리한가"** 로 판가름난다.
상대가 나를 2방에 잡으면 칼춤은 자살, 3방 이상 걸리면 이득. **이건 계산으로 나온다.**

### 3-4. 포켓몬이 체스보다 어려운 두 가지

**(1) 동시에 수를 낸다**

체스는 번갈아 두지만 포켓몬은 서로 모르는 채 동시에 고른다.
그래서 "최선의 수 하나"가 존재하지 않는 상황이 생긴다.
상대가 교체할 것 같으면 칼춤, 공격할 것 같으면 나도 공격 — 그런데 상대도 똑같이 생각한다.

이건 **확률을 섞어서 내는 것이 정답**인 문제다(가위바위보와 같음). 수학적으로 푸는 방법이 있다.

**(2) 상대의 정보를 모른다 — 여기서 로토덱스가 결정적이다**

상대가 어떤 기술·도구·노력치를 들고 있는지 모른다. 하지만 사용률이 있다.

```
한카리아스  지진 67%  스텔스록 39.6%  용성군 30.1%
            한카리아스나이트Z 35.3%  구애스카프 19%
            성격 명랑 24.2%  고집 21%
```

**"상대가 지진을 들고 있을 확률 67%"** 로 계산할 수 있다.
시중 계산기에는 없는 재료이고, 이 프로젝트의 핵심 무기다.

대전이 진행되면 정보가 늘어난다. 지진을 한 번 쓰면 100%로 확정되고,
예상보다 먼저 움직이면 스카프를 들었다는 뜻이다.
**관찰로 확률을 좁혀가는 것**까지가 완성형이다.

| **4-A** | 기술 4개 데미지 + **스피드 비교** ("내가 먼저 때리는가") | 쉬움 | 완료 |
| **4-B** | 변화기 환산 규칙 (랭크업·회복·상태이상) | 보통 | 완료 — 규칙표가 아니라 **턴 루프**로 했다 |
| **4-C** | 상대 기술을 확률로 다루기 (사용률 활용) | 보통 | 완료 |
| **5** | 2~3턴 앞 탐색 + 동시 수 처리 | 어려움 | 5는 교체로 바뀌고, 탐색은 **7**이 됐다 (끝까지 본다) |

**4-A가 생각보다 크다.** "내가 먼저 때려서 한 방에 잡는다"만 알아도 실전 판단의 절반은 끝난다.
스피드는 이미 데이터에 있으니 바로 됐다.

> **4-A 를 끝내고 나서 순서를 한 번 손봤다.** 4-B 를 위 3-3 표 같은 '환산 규칙표'로 쓰지 않고
> **1대1 턴 루프**로 대신하기로 했다. 목적은 그대로고 수단만 바뀐 것이다. 이유는 6장에 적었다.

### 3-6. 4-A 에서 실제로 한 것 — `best.py`

```
python best.py 메가보만다 하마돈
```

세 덩어리다.

**(1) 스피드 비교**

랭크 → 특성(속보) → 도구(구애스카프·검은철구) → 마비 순으로 곱한다.
도구 배율은 데미지 도구와 똑같이 **설명문에서 읽어내므로** 새 도구가 나와도 따라온다.

우선도는 기술마다 다르다. 그래서 머리말의 스피드 비교에서는 빼고 기술별 판정에서만 쓴다.
짓궂은마음(변화기 +1) · 질풍날개(HP 만땅 비행기 +1) · 시간벌기(항상 나중)까지 본다.
퀵드로·선제공격손톱처럼 확률로 뒤집는 것은 경고만 띄운다.

**(2) 상대 스피드를 모른다는 문제**

여기서 사용률이 한 번 더 일한다. 상대의 성격·노력치·도구 채용률을 곱해
**"상대 스피드가 얼마일 수 있는지"와 "내가 더 빠를 확률"**을 같이 낸다.

```
[스피드]  나 172  vs  상대 288   →  상대가 먼저 때린다
  상대 배분은 사실 모른다. 사용률로 보면 상대 스피드는 143 ~ 288 사이다.
    내가 더 빠를 확률  약 0.6%
    · 구애스카프 61.3% → 스피드 214 ~ 288  (이 경우 내가 후공)
    · 스피드 도구 없음 38.7% → 스피드 143 ~ 192
```

> 사용률에는 성격·노력치·도구가 **따로따로** 들어있고 "어떤 성격이 어떤 배분과 같이 쓰였는지"는
> 없다. 그래서 셋을 독립이라고 보고 곱한 **근사**다. 출력에도 그렇게 적어 둔다.
> 제대로 하려면 조합별 채용률이 필요한데 로토덱스가 그건 안 준다.

**(3) 대면 결론**

내가 몇 번 때려야 하는지, 상대가 몇 번 때려야 하는지를 선공/후공과 묶는다.

| | 이기는 조건 |
|---|---|
| 내가 선공 | 내 타수 ≤ 상대 타수 |
| 내가 후공 | 내 타수 < 상대 타수 |

난수 폭(운이 제일 좋을 때 / 제일 나쁠 때)까지 보고
**확실히 이김 / 난수 싸움 / 확실히 짐** 으로 가른다. 추천 기술은 이 결론으로 고른다.
데미지가 제일 센 기술이 아니라 **대면을 이기는 기술**을 고른다는 뜻이다.

**(4) 숫자를 믿으면 안 되는 기술 표시**

공격기 335개 중 **55개**는 위력 숫자만으로 안 된다. 설명문에서 알아내 `!` 로 표시한다.

| 종류 | 예 |
|---|---|
| 2턴 기술 | 솔라빔 — 첫 턴 데미지 0 |
| 연속 히트 | 바늘미사일 — 표시된 건 1회분 |
| 고정 데미지 | 나이트헤드 — 위력과 무관하게 50 |
| 위력 가변 | 자이로볼 — 1~150 |
| 반동 | 이판사판태클 — 준 데미지의 1/3 |
| 날씨·필드 의존 | 지진(그래스필드), 눈보라(눈일 때 필중) |

**배율을 찍어서 넣지는 않았다.** 아는 척해서 틀린 값을 넣느니 모른다고 말하는 편이 낫다
(4장의 원칙과 같다).

### 3-7. 4-A 가 아직 못 하는 것

- 변화기는 목록에만 나오고 점수가 없다 → **4-B**
- 상대 기술을 "가장 아픈 수" 하나로만 본다. 채용률 4%짜리 기술 때문에 결론이
  비관적으로 나오는 경우가 있다 → **4-C**
- 급소·교체·날씨/필드를 안 본다 → **전부 `battle.py` 턴 루프에 있다.**
  `best.py` 는 "한 턴을 잘라 봤을 때" 를 재는 자리라 일부러 여기까지만 본다
- 선제공격기에 붙은 조건(만나자마자는 나온 첫 턴만, 기습은 상대가 공격기일 때만)을 안 본다

## 5. 자가발전 계획

### 전제 조건 딱 하나

> **AI가 스스로 대전을 해볼 수 있어야 한다.**

| | 하루에 둘 수 있는 판수 |
|---|---|
| 실제 게임 | 100판 정도 |
| 시뮬레이터 | 수십만 판 |

**시뮬레이터의 완성도가 자가발전 속도의 상한선이다.** 여기가 부실하면 위에 뭘 올려도 소용없다.

### 방법 (쉬운 순서)

**A. 자기대전 + 통계 축적** — 지금 데이터로도 가능

같은 상황에서 A안과 B안을 각각 1만 번씩 돌려 승률을 비교한다.

> "한카리아스가 하마돈 앞에서 칼춤 vs 지진 → 칼춤 승률 58%, 지진 52%"

학습이라기보단 **실험**이다. 대신 확실하고 **왜 그런지 설명이 된다.**

**B. 평가 기준 자동 조정** — 가성비가 제일 좋음

AI가 상황에 점수를 매길 때 쓰는 숫자들:

```
내 HP 1% 의 가치        = ?
공격 랭크 1단계의 가치   = ?
상대를 마비시킨 가치     = ?
스텔스록 깔아둔 가치     = ?
```

처음엔 사람이 감으로 정하고, **숫자를 조금씩 바꾼 여러 AI를 서로 붙여 이긴 쪽을 남기고 변형**시킨다.
수백 세대면 사람이 정한 값보다 훨씬 나아진다. 개인 PC로 충분하다.

**C. 탐색 깊이 늘리기** — 계산 시간이 곧 실력

2턴 → 4턴 → 6턴. 엄밀히는 자가발전이 아니라 "더 오래 고민하기"지만 효과는 확실하다.

**D. 강화학습 자기대전** — 가장 강하지만 가장 어려움

알파고 방식. 다만 포켓몬은 **상대 패를 모르고 동시에 수를 내서** 바둑보다 까다롭다.
오히려 포커 AI가 쓰는 방법(후회 최소화 계열)이 더 맞을 수 있다. 계산 자원이 많이 든다.

**A와 B까지가 현실적인 목표이고, 그것만으로도 충분히 강해진다.**

### "결국 최선의 수에 도달하는가"

- **이론적으로** 도달점은 존재한다 (경우의 수가 유한하므로)
- **현실적으로** 완전 해결은 불가능하다 (경우의 수가 천문학적)
- **하지만 "사람이 이길 수 없는 수준"에는 도달 가능하다**

### 중요한 구분

| | 뜻 | 특징 |
|---|---|---|
| 균형 전략 | 상대도 완벽하다고 가정한 최선 | 크게 지지 않음. 대신 약한 상대도 크게 못 이김 |
| **착취 전략** | 실제 사람들의 경향을 파고드는 최선 | 훨씬 크게 이김. 대신 예상 밖 상대에게 당함 |

**이 프로젝트는 두 번째에 유리하다.** 로토덱스 사용률이 곧 "사람들이 실제로 뭘 하는지"의 기록이기 때문이다.

### 자가발전의 두 가지 함정

1. **틀린 규칙을 최적화** — 4장의 세 가정을 먼저 확정할 것
2. **목표를 잘못 정의** — "HP를 높게 유지하라"고만 가르치면 공격을 안 하고 회복만 하다 시간패한다

|---|---|
| 공격기 · 랭크업기 · 회복기 · 상태이상기 | **저절로 나온다. 규칙을 쓸 필요가 없다** |
| 압정·스텔스록 · 교체 | 어차피 파티가 있어야 계산된다 |

6줄 중 4줄이 공짜다. 손으로 쓴 환산 규칙은 나중에 버릴 코드이고,
무엇보다 **틀렸는지 알기 어려운** 종류다 — 4장·5장이 경고하는 바로 그 함정.
그리고 턴 루프는 어차피 탐색·자가발전이 요구하는 전제조건이다.

### 교체 · 파티 · 날씨는 언제 붙이나

세 개를 한 덩어리로 보면 안 된다. **성격이 다르고 붙일 시점도 다르다.**

| | 정체 | 언제 |
|---|---|---|
| **날씨·필드** | 전역 상태 변수 2개 + 턴 카운터 | **턴 루프와 같이.** 미루면 제일 비싸다 |
| **교체** | 게임 트리의 모양을 바꾸는 새 행동 | 턴 루프를 손으로 검산한 **직후** |
| **파티** | 교체의 전제 | 교체와 한 덩어리 |

#### 날씨·필드 — 미루면 안 된다

선택이 아니라 **기본값**이기 때문이다.

| 순위 | 포켓몬 | 특성 | 채용률 |
|---|---|---|---|
| 4 | 하마돈 | 모래날림 | **99.8%** |
| 10 | 고릴타 | 그래스메이커 | **99.8%** |
| 22 | 에써르 | 사이코메이커 | 99.9% |
| 23 | 나인테일 | 눈퍼뜨리기 | 99.9% |

전부 `등장 시 5턴 동안 ~ 상태로 만든다` 다. **나오기만 하면 깔린다.**
즉 상위권 대면의 상당수는 1턴째부터 이미 날씨가 있는 상태다.

지금 당장 틀리고 있는 것:

- `best.py 메가보만다 하마돈` — 이 문서의 대표 예제인데, 하마돈이 나오는 순간 모래바람이다.
  보만다(드래곤/비행)는 매 턴 칩댐을 받는다. "확정 2타로 이김" 이 흔들린다.
- **고릴타(10위) 앞에서는 지진 위력이 절반이다.** 추측이 아니라 데이터에 박혀 있다 —
  `지진: 그래스필드 상태일 때 위력이 1/2이 된다`.

그런데 **날씨는 교체도 파티도 필요 없다.** 상태 변수 두 개(종류, 남은 턴)면 끝이다.
그리고 바로 그래서 **나중에 끼워 넣는 비용이 제일 비싸다.** 전역 상태라
뒤늦게 넣으면 데미지 계산 호출부를 전부 건드려야 한다.

**단, 효과는 두 종류로 갈라서 넣는다.**

| | 양 | 처리 |
|---|---|---|
| 게임 데이터에 **적혀 있는** 것 | 기술 40개 · 특성 30개 | 바로 구현. 확실함 |
| 데이터에 **없는** 것 — 모래 칩댐, 바위 특방 보정, 필드 타입 강화, 사이코필드 선공 차단 | — | **CONFIG 미확인 가정값** + 실측 대상 |

이 구분이 중요하다. `모래바람` 설명문은 "5턴 동안 모래바람 상태로 만든다" 가 전부다.
**칩댐이 몇 분의 1인지, 바위가 특방을 얼마나 받는지는 게임 데이터 어디에도 없다.**
본편 값을 가정해야 하고, 그러면 미확인 가정값이 지금 4개에서 더 늘어난다.
4장 원칙대로 한 곳에 모으고 시끄럽게 표시할 것.

범위는 줄일 수 있다 — **날씨 의존 스피드 특성(쓱쓱·엽록소·모래헤치기·눈치우기)은 상위 50에 0건**이다.
안 해도 된다.

#### 교체·파티 — 턴 루프 검산 직후. 단 두 층으로 나뉜다

기본 룰이 **6마리 파티 → 3마리 선출**이라 파티 층이 두 개로 갈린다.
자세한 것은 바로 다음 절에.

| 층 | 무엇 | 배틀 내인가 |
|---|---|---|
| **대전 중 교체** | 턴 안에서 바꾼다. 압정·강제 교체기가 여기 붙는다 | **맞다** → 먼저 |
| **선출** (6→3) | 대전 **시작 전**, 상대 6마리를 보고 3마리를 고른다 | 아니다 → 나중 |

목표가 "배틀 내에서의 최선의 수" 이므로 **대전 중 교체를 먼저** 한다.
선출은 싸긴 하지만 대전 시작 전의 결정이고, 무엇보다
**선출의 품질은 배틀 엔진 품질의 함수**라 엔진을 먼저 올리는 편이 이득이다.

**왜 더 미루면 안 되나**

- **하마돈(4위)의 2위 기술이 날려버리기 62.3%** 다. 강제 교체기라 **파티가 없으면 아예 모델이 안 된다.**
  한카리아스 드래곤테일 26.7%, 브리두라스 울부짖기 31.3% + 드래곤테일 22.5% —
  **상위 8마리 중 3마리**가 상대를 강제로 바꿔 버린다.
- **스텔스록·압정을 상위 50 중 11마리가 깐다** (하마돈 92.5%, 엠페르트 65.3%,
  킬라플로르 63.9%, 브리두라스 61.3%). 3-3 표에서 "교체할 때마다 누적" 이라
  교체가 없으면 값이 영원히 0이다.
- 그리고 여기가 인프라가 물건이 되는 지점이다.

**왜 턴 루프와 동시에는 안 되나**

**1대1 턴 루프는 손으로 검산할 수 있다.** "하마돈이 게으름피우기를 쓰면 몇 턴 버티나" 는
산수로 확인된다. 교체가 섞인 3대3은 안 된다.
4장이 경고한 "조용히 틀리는 것" 을 잡으려면 **검산 가능한 상태를 한 번 통과**해야 한다.
거기를 건너뛰면 나중에 승률이 이상해도 원인이 규칙인지 탐색인지 구분이 안 된다.

그리고 교체가 들어오는 순간 **"동시에 수를 낸다"(3-4(1))가 진짜 문제가 된다** —
교체야말로 가위바위보를 만드는 수다. 별개의 난이도이므로 섞지 않는 편이 낫다.

> **한 줄로 — 날씨는 "지금 자리를 안 만들면 나중에 전부 뜯어고쳐야 하는 것",
> 대전 중 교체는 "지금 만들면 검산이 불가능해지는 것"이다.**
> 그래서 하나는 당기고 하나는 한 칸 미룬다.
> 선출(6→3)은 대전 시작 전의 결정이라 그 뒤로 뺐다.

### 대전 형식 — 6마리 파티에서 3마리를 선출한다

**기본 룰이 6대6이 아니라 6마리 파티 → 3마리 선출이다.** 이게 여러 군데를 바꾼다.

#### (1) 대전이 시작되기 전에 이미 한 번 '동시에 수를 낸다'

서로의 6마리를 보고 **동시에** 3마리를 고른다. 3-4(1) 의 가위바위보 문제가
대전 중이 아니라 **대전 시작 전에 먼저** 일어난다.

다만 대전 중보다 훨씬 작고 깔끔한 게임이다.

```
내가 고를 수 있는 조합   6C3 = 20가지
상대도                  20가지
합쳐서                  400 조합  ← 전부 훑어볼 수 있는 크기다
```

그리고 **페어와이즈 대면 승률만 있으면 근사가 된다.** 만들기는 싸다.
다만 그 승률이 엉성하면 선출 추천도 엉성하므로, 배틀 엔진을 먼저 올린 뒤에 한다.

#### (2) 제품 마일스톤이 바뀐다

앞에 "내 6마리가 상위 20마리에게 몇 %로 이기나" 라고 적었는데, 그건 6대6 감각이었다.
실제 게임에서 사람이 하는 일은 이쪽이다.

> **"상대 6마리를 봤다. 내 6마리 중 어떤 3마리를 뽑아야 하나."**

다만 이건 대전 **시작 전**의 결정이다. 목표가 "배틀 내에서의 최선의 수" 이므로
대전 중 교체(5단계)를 먼저 하고 그 다음에 한다.

#### (3) 6마리 파티의 의미가 달라진다

**6마리가 전부 강할 필요가 없다. 서로 다른 상대를 커버하면 된다.**
그래서 팀빌딩 지표는 "평균 승률" 이 아니라 **커버리지** 여야 한다 —
"상대가 어떤 6마리를 들고 와도 뽑을 만한 3마리가 있는가".

#### (4) 압정·강제 교체기의 가치가 커진다

3마리뿐이라 **교체할 여지 자체가 적다.** 강제로 바꾸게 만드는 수가 그만큼 세진다.
하마돈(4위)이 하품 96.3% + 날려버리기 62.3% + 스텔스록 92.5% 를 한꺼번에 드는 이유가 이것이다.

거꾸로 스텔스록의 값어치를 **본편 6대6 감각으로 재면 과대평가**가 된다.
3-3 표의 "남은 턴이 길수록 가치가 크다" 를 3마리 기준으로 다시 재야 한다.

#### (5) 탐색이 현실적인 크기가 된다

6대6이 아니라 3대3이다. 탐색 단계의 부담이 눈에 띄게 줄어든다.

#### (6) 확인 못 한 것 — 로토덱스 `rank` 의 기준

사용률 데이터에는 `rank` 만 있고 **선출률이 없다.** 그리고 그 rank 가
**파티에 넣은 비율인지, 실제로 뽑아서 싸운 비율인지 모른다.** 둘은 다르다.

| | 뜻 |
|---|---|
| 파티 채용률 | 6마리 안에 넣은 비율 |
| 선출률 | 실제로 3마리에 뽑혀 나온 비율 |

"상대로 만날 확률" 을 쓰려면 **선출률이 맞다.** 4-C 에서 상대를 분포로 다룰 때
이 구분이 그대로 정확도로 이어지므로, 로토덱스 원본에서 확인할 것.
(`build_usage.py` 는 `ranking.json` 의 `rank` 를 그대로 옮기고 있다.)

### 순서

1장 진행표와 **같은 번호**를 쓴다. 실측은 단계가 아니라 선행 조건이라 번호를 안 붙인다.

**[선행] 미확인 값 실측** — *사용자만 할 수 있는 일, 10초*

~~자속~~ · ~~급소~~ (둘 다 2026-09-17 확정) · 화상 · 마비. 방법은 4장에 적어 뒀다.
안 해도 진행은 되지만, 나중에 틀리면 역추적이 어려워진다.

---

**4-B. 1대1 턴 루프 (`battle.py`) + 날씨·필드** — 완료

교체 · 파티 **없이** 시작한다. 날씨는 **자리(상태 변수)를 반드시 만들고**,
효과는 데이터에 적힌 것부터 넣는다.

- HP · 랭크 · 상태이상
- 1회용 도구 (자뭉열매 · 기합의띠 · 풍선)
- 명중률 · 급소 확률 · 반동 · 회복
- 날씨 · 필드 (종류 + 남은 턴) — 등장 시 자동으로 까는 특성 4종 포함

> **내놓는 답은 승패가 아니라 '끝났을 때의 상태' 다.** 아래 별도 절 참고.
> 이걸 틀리면 나중에 전부 뜯어고쳐야 한다.

**완료 조건 — 손으로 검산이 된다.**
"하마돈이 게으름피우기를 쓰면 몇 턴 버티나" 를 산수로 맞춰 본다.
1대1 구조에서만 가능한 마지막 지점이므로 여기를 통과하지 못하면 앞으로 가지 않는다.

**4-C. 상대를 하나가 아니라 분포로** — 완료 (`scout.py`)

지금은 "가장 아픈 수" 하나로만 보는데, 채용률 4%짜리 기술 때문에 결론이 지나치게 비관적으로 나온다.
스피드 분포에서 이미 해 본 방식을 기술에도 쓴다.
여기에 **관찰로 좁히기**(3-4(2) — 지진을 한 번 쓰면 100% 확정, 예상보다 먼저 움직이면 스카프)를 붙이면
시중 계산기에 없는 이 프로젝트만의 무기가 완성된다.

**5. 대전 중 교체 + 압정 + 강제 교체기** — 완료

교체는 대전 중에 두는 수 하나이므로 이것도 '배틀 내 최선의 수' 다.
상위 20마리 서로 대면 380건 중 **40.5% 가 "확실히 짐"** 으로 나왔는데,
그 답들의 진짜 최선수는 대개 **빠지는 것**이었다. 전에는 그 답을 표현조차 못 했다.

```
python battle.py 메가보만다,아머까오,고릴타 브리두라스

계획                              승률
지진                              45.5%
고릴타 로 교체 → 10만마력         39.5%   ← 전에는 이 답을 표현조차 못 했다
역린                              12.5%
```

들어간 것

| | 내용 |
|---|---|
| **물러나면 랭크가 사라진다** | 제일 중요한 규칙. '용의춤을 쌓았으면 안 빠져야 한다' 가 여기서 나온다 |
| 압정 4종 | 스텔스록(바위 상성을 탄다) · 압정뿌리기(겹칠수록) · 독압정 · 끈적끈적네트 |
| 떠 있으면 안 밟는다 | 비행·부유는 압정을 안 밟지만 **스텔스록은 밟는다** |
| 독타입은 독압정을 걷어 간다 | |
| 강제 교체기 | 날려버리기·울부짖기·드래곤테일 — **쌓은 랭크를 통째로 날린다** |
| 흡반·파수견 / 그림자밟기 | 강제 교체를 막는다 / 상대가 못 빠진다 |
| **위협** | 보만다(1위) 99.3%, 갸라도스(14위) 99.4%. 나올 때마다 상대 공격 −1 |
| 쓰러진 자리 채우기 | 파티가 다 쓰러져야 끝난다 |

압정 수치는 **게임 데이터에 없다.** 설명문이 "상대 필드를 스텔스록 상태로 만든다"
뿐이라 본편 값을 가정했고 `calc.CONFIG` 에 모아 경고를 띄운다.

여기서 랭크업의 값어치도 비로소 제대로 나온다. 쌓아 두면 후속까지 이어지지만,
빠지면 사라지고 강제 교체기에 밀려도 사라진다.

#### 빼는 것과 내주는 것은 값이 다르다

**불리하다고 늘 빼는 것이 답은 아니다.** 둘의 값이 다르기 때문이다.

| | 치르는 값 | 얻는 것 |
|---|---|---|
| **뺀다** | 들어오는 놈이 **그 턴에 한 대 맞는다** + 압정 | 뺀 놈이 살아남는다 (쌓은 랭크는 사라진다) |
| **내준다** | 한 마리를 잃는다 | 다음 놈이 **공짜로** 나온다 (그 턴에 안 맞는다) + 압정만 |

실제로 이렇게 갈린다.

```
python battle.py 메가보만다,아머까오,고릴타 브리두라스,하마돈

계획                       승률    이길 때 잃는 마릿수   남는 파티 HP
지진 (버틴다)              19.3%   1.66마리              25%
고릴타 로 교체             10.0%   2.00마리              17%   ← 빼는 쪽이 더 나쁘다
```

빼면 고릴타가 브리두라스의 용성군을 그대로 맞고 나오므로, 결국 둘 다 잃는다.
그냥 버티면 보만다 한 마리로 끝날 수도 있다.

그래서 승률만 보지 않고 **'이길 때 몇 마리를 잃었나' 와 '남는 파티 HP' 를 같이 센다.**
파티가 있을 때는 이 둘로 순위를 가른다.

> 같이 고친 것 — 교체돼 나온 놈이 **자기 기술을 쓰도록** 했다(`Policy`).
> 전에는 계획이 리드의 수순 그대로라 고릴타가 보만다의 이판사판태클을 쓰려 들었다.
> 배우지도 않은 기술이라 조용히 이상한 계산이 되던 자리다.

#### 누구를 내보낼지 — HP 만으로는 못 정한다

처음에는 "남은 것 중 HP 비율이 제일 높은 놈" 으로 두었는데 **틀린 기준이다.**

> **필요한 HP 는 상대마다 다르다.**
> 물어야 할 것은 "이 상대를 상대하려면 몇 대를 버텨야 하고, 지금 HP 로 그게 되는가" 다.

양쪽 다 어긋난다.

| | HP | 실제 값어치 |
|---|---|---|
| **따라큐** (탈 살아있음 + 야습 우선도 +1, 채용률 95.3%) | 30% | 한 대를 통째로 막고, 스피드와 상관없이 때린다. **확실히 두 대는 넣는다** |
| **느리고 한 방에 죽는 놈** | 100% | 맞고 죽는다. **한 대도 못 넣는다** |

실제로 재 보면 이렇게 나온다 (상대: 브리두라스).

```
따라큐(HP 30%)     2.09
킬라플로르(HP 100%) 2.30
누리레느(HP 100%)   0.81   ← HP 로 골랐으면 이놈이 1순위였다
```

그래서 기준을 **타수** 로 바꿨다. `best.race` 와 같은 셈법이다.

1. 나오면서 압정을 밟고도 살아 있는가 (밟고 죽으면 최하)
2. 내가 이 상대를 잡는 데 몇 대 — **상대의 지금 HP 기준**
3. 상대가 나를 잡는 데 몇 대 — **내 지금 HP 기준**.
   탈·옹골참·기합의띠는 여기서 한 대를 벌어 준다
4. 선공 여부와 묶어 **죽기 전에 몇 대나 넣는지**를 센다

점수 = 넣는 데미지 + (잡으면 보너스) + (살아남으면 남은 HP 만큼 조금)

고른 이유는 로그에 남는다 (`누구를 낼까 — 따라큐(HP 30%) 2.09 / 누리레느(HP 100%) 0.81`).
나중에 실전에서 지고 나서 되짚어야 하므로.

> 아직 남은 것 — 이건 **한 번의 교환**만 본다. 뒤에 뭐가 더 있는지,
> 압정을 몇 번 더 밟을지까지는 안 본다. 제대로 하려면 여기서도 턴을 돌려야 한다.

### 4-B 에서 실제로 한 것 — `battle.py`

```
python battle.py 메가보만다 하마돈
python battle.py 메가보만다 하마돈 --기록       한 판을 턴별로 찍어 본다
python battle.py 메가보만다 하마돈 --계획 용의춤,이판사판태클
```

메가보만다 vs 하마돈에서 실제로 이렇게 갈린다.

| 계획 | 승률 | 남는 HP | 남는 랭크 | 남는 몸 |
|---|---|---|---|---|
| 역린 | 100% | 89% | 없음 | 89 |
| **용의춤 → 용의춤 → 이판사판태클** | 100% | 38% | **공격+2 스피드+2** | **98** |

**승률이 같아도 남는 몸이 다르다.** 뒤쪽을 고른다.

#### 들어간 것

- **변화기 효과를 게임 설명문에서 읽는다** — 랭크·회복·상태이상·보호·강제교체·날씨·압정.
  도구·특성과 같은 방식이다. 상위 20마리가 쓰는 변화기 19개를 전부 읽는다.
- **날씨·필드** — 등장만으로 까는 특성 4종, 5턴 지속, 모래 칩댐,
  그래스필드의 지진 반감(데이터에 명시된 것).
- **1회용 도구** — 자뭉열매(하마돈 66.8%), 기합의띠, 먹다남은음식, 생명의구슬 반동.
- **턴이 있어야 되는 특성** — 탈(따라큐 100%), 옹골참, 지구력(브리두라스),
  까칠한피부(한카리아스 99.1%), 열교환(드닐레이브).
  **2장에서 '메타 상위권인데 못 한다' 고 꼽은 4개가 여기서 다 들어갔다.**
- 명중률 · 급소 · 마비 행동불가 · 반동. 난수가 있으므로 몬테카를로로 승률을 낸다.

#### 상태 이상 — 출처를 둘로 갈라서 넣었다

나무위키·불바피디아로 본편 값을 대조했고, **내가 쓰던 가정값이 전부 본편(7세대 이후)과
일치했다.** 다만 챔피언스에서 확인한 것은 여전히 아니다.

| | 쓰는 값 | 본편 |
|---|---|---|
| 화상 물리 반감 / 턴당 | 0.5 / 1/16 | 같음 (1/16 은 1·7세대 이후 값. 2~6세대는 1/8) |
| 마비 스피드 / 행동불능 | 0.5 / 25% | 같음 (0.5 는 7세대 이후. 그 전은 0.25) |
| 독 턴당 | 1/8 | 같음 |
| 맹독 | 1/16 씩 누적 | 같음 |
| 모래 턴당 / 바위 특방 | 1/16 / 1.5배 | 같음 |
| 잠듦 지속 | 2~4턴 | 같음 (5세대 이후) |

**그런데 게임 데이터가 본편과 다른 것을 하나 찾았다.**

> `잠자기` 설명문 — "2턴 동안 잠듦 상태가 된다". **본편은 3턴이다.**

그래서 잠자기만은 게임 데이터를 따랐다. 이런 것이 더 있을 수 있으므로
**본편 값을 넣기 전에 게임 설명문부터 볼 것.**

면역은 출처가 갈린다.

| | 어디서 | 개수 |
|---|---|---|
| **특성 면역** | 게임 설명문에 그대로 적혀 있다 — 읽어서 쓴다 | 9개 (유연·불면·면역·마그마의무장·의기양양·스위트베일·아로마베일·수포·열교환) |
| **기술별 타입 면역** | 게임 설명문에 적혀 있다 | 4개 (독가루·저리가루·수면가루 → 풀, 전기자석파 → 땅) |
| **타입 자체의 면역** | **게임 데이터 어디에도 없다.** 본편 규칙 가정 | 불꽃→화상, 전기→마비, 독·강철→독, 얼음→얼음 |

마지막 줄만 `calc.STATUS_TYPE_IMMUNE` 에 모아 뒀고, 걸릴 때마다
"게임 데이터에 없는 본편 규칙 가정입니다" 경고를 띄운다.

#### 랭크 1단계는 HP 몇 % 인가 — `RANK_VALUE`

위 표에서 "HP 89% 남기고 이기기" 와 "공격+2 스피드+2 남기고 이기기" 중
무엇을 고를지는 이 숫자 하나가 정한다. 지금은 **사람이 감으로 박은 15** 다.

**5장 B('평가 기준 자동 조정')가 바로 이 숫자를 맞추는 단계다.** 여기가 그 첫 손잡이다.

#### 조용히 틀리던 것 세 개

만들면서 잡았다. 셋 다 **결과가 그럴듯하게 나와서 눈치채기 어려운** 종류였다.

| 무엇 | 왜 |
|---|---|
| 용의춤이 **공격 −1** 이 됐다 | `'올린'.startswith('올리')` 가 거짓. 한글은 '린'과 '리'가 다른 한 글자다 |
| 칼춤·나쁜음모가 통째로 안 읽혔다 | 받침에 따라 조사가 '공격**을**' / '방어**를**' 로 갈리는데 '을' 을 안 받았다 |
| 필드 배율이 한 번도 안 걸렸다 | 필드 이름을 문자열로 잘라 타입을 얻으려 했다 (`'그래스필드'[:-2]` → '그래스') |

스피드 도구 때(`되` vs `된`)와 같은 함정이 또 나왔다. **한글 어미·조사로 정규식을
끊지 말 것.** 셋 다 `tests.py` 에 박아 뒀다.

### 4-C 에서 실제로 한 것 — `scout.py`

```
python battle.py 메가보만다 하마돈 --분포
python battle.py 메가보만다 하마돈 --분포 --봤다 얼음엄니
```

매 판 상대를 **사용률대로 새로 뽑아서** 싸운다. 나오는 승률이
'실제로 만날 상대들을 평균한 값' 이 된다.

#### 채용률을 그대로 확률로 써도 되는 근거를 찾았다

기술 채용률의 합이 포켓몬마다 **평균 376%** 다.

```
하마돈  지진 97.7 + 하품 96.3 + 스텔스록 92.5 + 날려버리기 62.3 + 게으름피우기 37.5 + ...  = 398.2%
```

기술칸이 4개이므로, 채용률을 **'그 4칸에 들어 있을 확률' 로 그대로 쓸 수 있다**는 뜻이다.
(400%에 못 미치는 나머지는 상위 10개 밖의 자잘한 기술들이다.)

#### 그런데 그냥 뽑으면 채용률이 안 맞는다

칸이 4개뿐이라 그냥 던지면 자주 넘친다. 넘쳤을 때를 어떻게 처리하든 어긋난다.

| 방법 | 결과 |
|---|---|
| 넘치면 채용률 높은 쪽을 남긴다 | 게으름피우기 37.5% → **17.3%** |
| 넘치면 다시 던진다 | 게으름피우기 37.5% → **20.8%** |
| **조건부로 직접 뽑는다** | 게으름피우기 37.5% → **38.2%** ✅ |

다시 던지는 방식이 왜 안 되는지가 재미있다. 하마돈은 채용률 합이 398% 라
**독립해서 던졌을 때 4칸 이하가 나올 확률이 0.2% 밖에 안 된다.** 200번 다시 던져도
거의 전부 실패해서 결국 "상위 4개" 만 나온다.

그래서 두 단계로 했다.

1. `fit_weights` — '4칸 이하' 조건을 걸어도 원래 채용률이 나오도록 가중치를 역산한다
   (승산 위에서 반복해 맞춘다. 확률을 그대로 곱하면 튄다).
2. `sample_conditional` — 앞에서부터 하나씩 정하면서 남은 칸으로 뒤쪽이 들어갈 수 있는지를
   매번 따진다. **다시 던지지 않으므로 몇 %든 정확하다.**

맞았는지는 `check_marginals` 로 직접 잰다. 지금 **최대 어긋남 1.1%p** (몬테카를로 오차 수준).

#### 이게 이 프로젝트의 무기다 — '졌을 때 상대는 이랬다'

승률 하나만 내놓지 않고, **무엇이 나를 이겼는지**와 **그게 평소 얼마나 나오는지**를 견준다.

```
[졌을 때 상대는 이랬다]
  · 기술 '얼음엄니' — 졌을 때 100% 에 있었다 (평소 5%, 21.4배)
```

읽는 법은 이렇다.

| 위에 뜬 것이 | 뜻 |
|---|---|
| 평소 잘 안 나오는 것 | **운 나쁘면 지는** 경우. 대면 자체는 유리하다 |
| 자주 나오는 것 | **진짜로 불리한** 대면 |

5장의 '착취 전략' 이 여기서 처음 손에 잡힌다.

#### 관찰로 좁히기 (3-4(2))

`--봤다` 로 실제로 본 기술을 넣으면 그 기술의 확률이 100% 로 고정된다.

```
아무것도 모를 때        승률 96.3%
얼음엄니를 봤을 때      승률 20.4%
```

`Evidence` 에 스피드 하한·도구·특성 자리도 만들어 뒀다.
("예상보다 먼저 움직였다 → 스카프" 같은 추론이 들어갈 자리다.)

#### 알아낸 데이터 문제 — 노력치 채용률 합이 ~162% 다

| | 합계 |
|---|---|
| 도구·성격·특성 | ~100% (정상) |
| **노력치** | **평균 162%, 최대 200%** |

같은 배분이 두 번 들어 있는 경우가 있는데(하마돈 `HD` 30.6% + `HD` 0.9%),
**그걸 합쳐도 설명이 안 된다.** `build_usage.py` 는 원본을 그대로 옮기고 있으므로
로토덱스 원본 단계의 문제다. 지금은 정규화해서 쓰고 있다.
원본(`../pokemon_dashboard`)을 볼 수 있을 때 확인할 것.

### 턴 루프가 내놓을 답 — 승패가 아니라 '끝났을 때의 상태'

**이건 설계 결정이고, 틀리면 나중에 전부 뜯어고쳐야 한다.**

턴 루프를 "이 대면을 이기나 지나" 로 만들면 이렇게 답한다.

> "그냥 때려도 이기는데 뭐하러 용의춤을 씁니까"

**틀렸다.** 어차피 이기는 대면이야말로 쌓아둘 자리다.
**쌓아놓은 랭크는 상대가 쓰러져도 그대로 남아서 다음, 그 다음 포켓몬까지 따라간다.**
승패만 보면 이 값어치가 통째로 안 보인다.

```
잘못된 설계   ->   "이겼다"
맞는 설계     ->   "이겼다. 끝났을 때 내 HP 62%, 공격+1, 스피드+1, 자뭉열매 씀"
```

**끝났을 때의 상태를 통째로 넘겨준다.** 그게 그대로 다음 포켓몬 상대의 시작 상태가 된다.
이렇게 해두면 5단계에서 후속 포켓몬을 붙일 때 **턴 루프를 다시 짜지 않아도 된다.**
그냥 이어 붙이면 된다.

#### 랭크업과 강제 교체기는 동전의 양면이다

상위권에 이게 왜 깔려 있는지가 여기서 설명된다.

| 포켓몬 | 기술 | 채용률 |
|---|---|---|
| 하마돈 (4위) | 날려버리기 | 62.3% |
| 브리두라스 (8위) | 울부짖기 | 31.3% |
| 한카리아스 (2위) | 드래곤테일 | 26.7% |

전부 설명문이 `상대에게 교체할 포켓몬이 있는 경우 랜덤한 포켓몬으로 교체시킨다` 다.
**쌓아놓은 랭크를 통째로 날려버리는 수**다.

즉 **랭크업의 값어치와 강제 교체기의 값어치는 같은 축 위에 있다** — "후속까지 이어지는가".
한쪽만 계산에 넣으면 나머지 한쪽이 반드시 틀린다.

### 상대도 빠진다 — 제일 컸던 편향

시뮬레이터 안의 상대가 **죽을 때까지 절대 안 빠졌다.** 실제 사람은 불리하면 뺀다.
그래서 내 승률이 실제보다 한참 높게 나오고 있었다. 재 보니 한 대면에서
**59.2% → 3.6%** 까지 벌어졌다.

고치면서 알게 된 것 하나. **교체 판단을 어림셈으로 하면 카운터를 못 알아본다.**

```
상대 리드 메가보만다 / 내 리드 누리레느
  그대로 있기   1.000
  타부자고      공짜로 나오면 2.300  /  한 대 맞고 나오면 0.598   ← 안 빼게 된다
```

한 번의 교환만 보는 점수로는 "한 대 맞고 들어가면 손해" 로만 보인다.
그래서 **대전 시작 전에 1대1 승률표를 한 번 재 두고**(`matchup_table`),
교체 판단은 추측이 아니라 그 표로 한다. 표는 캐시하므로 값이 거의 안 든다.
(`pick.py` 의 상성표와 같은 것이라 그대로 돌려 쓴다.)

점수 구조도 고쳤다. 전에는 '깎은 양' 과 '잡았음' 을 그냥 더해서
**사이좋게 비기는 놈이 확실히 이기는 놈과 같은 점수**가 나왔다.
이기면 1.0 이상, 못 이기면 0.6 이하로 확실히 갈랐다.

### 가정값 감도 — 무엇을 먼저 실측해야 하는가 (`sensitivity.py`)

`CONFIG` 의 미확인 값이 스무 개가 넘는데 다 실측할 수는 없다.
그래서 **하나씩 흔들어 보고 답이 실제로 바뀌는 것만 골라냈다.**

```
python sensitivity.py
```

접전 대면 5개 x 가정값 16개를 재 본 결과다.

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 최대 흔들림 |
|---|---|---|
| **급소 1.5 → 2.0** | **1 / 5** | 0.8%p |
| **자속 1.5 → 2.0** | 0 / 5 | **53.3%p** |
| 나머지 14개 (화상·독·마비·모래·필드·잠듦·혼란·압정…) | 0 / 5 | 0.0%p |

**결론이 아주 선명하다.**

> **스무 개 중 실측이 필요한 것은 두 개다 — 자속과 급소 배율.**
> 나머지는 지금 값이 틀려도 답이 안 바뀐다.

그리고 둘의 성격이 다르다.

| | 뜻 |
|---|---|
| **급소 배율** | **추천 자체를 바꾼다.** "뭘 누를까" 가 틀릴 수 있다 |
| **자속 배율** | 추천은 그대로인데 **승률이 53%p 흔들린다.** 학습의 보상이 그만큼 틀린다 |

이것이 4장의 경고를 숫자로 확인한 것이다 —
**"뭘 누를까" 는 지금 믿어도 되고, "이 판을 이기나" 는 자속을 재기 전까지 믿으면 안 된다.**

> `0.0%p` 는 "그 값이 안 중요하다" 가 아니라 **이 대면들에서 그 조건이 안 나왔다**
> 는 뜻일 수도 있다. 화상이 안 걸리는 대면에서는 화상 칩댐을 흔들어도 0 이다.
> 그 값이 걸리는 대면을 따로 넣어 다시 재 볼 것.

### 나중에 — 실전에서 돌려보고 진 이유를 따진다

대화만으로 완성하는 데는 한계가 있다. 그래서 다음 단계가 예정돼 있다.

> **도구가 고른 수대로 실제 게임을 두고, 졌을 때 왜 졌는지 분석한다.**

이게 이 프로젝트에서 **유일하게 진짜인 검증**이다.
시뮬레이터 안의 승률은 아무것도 증명하지 않는다(4장). 실전에서 진 판은 증명한다.
진 이유는 셋 중 하나이고, 셋을 갈라내는 것이 목표다.

| 진 이유 | 고칠 곳 |
|---|---|
| 규칙·가정이 틀렸다 | `CONFIG` 미확인 값, 특성·기술 구현 |
| 계산은 맞는데 판단이 나빴다 | 평가 기준 (5장 B) |
| 그냥 운이 나빴다 | 고칠 것 없음 |

#### 그래서 지금부터 지켜야 할 것

**도구는 판단의 근거를 남겨야 한다.** "용의춤 쓰세요" 만 출력하고 지면 분석이 불가능하다.
한 판이 끝난 뒤 되짚을 수 있도록 매 수마다 이만큼을 기록해 둘 것.

- 상대를 무엇이라고 **가정**했는가 (배분 · 도구 · 기술 · 확률)
- 어떤 수들을 비교했고 각각 **몇 점**이었는가
- **무슨 일이 일어날 것으로 예상**했는가 (예상 데미지 · 예상 타수 · 선공 여부)

실제로 일어난 일과 이 기록을 맞대 보면, 위 표의 셋 중 어느 것인지가 갈린다.
`battle.py` 를 만들 때부터 이 기록을 남기게 할 것. 나중에 붙이면 늦다.

### 4-C 에서 반드시 짚어야 할 것 — 채용률은 '그 개체가 들고 있을 확률'이 아니다

4-B 를 만들면서 이게 결론을 통째로 뒤집는 것을 실제로 봤다.

처음에는 상대가 **사용률 목록에서 제일 아픈 수**를 쓴다고 놓았다.
메가보만다 vs 하마돈에서 그게 **얼음엄니(채용률 4.0%)** 였고, 승률이 22% 로 나왔다.
채용률 4% 짜리 기술을 100% 확정으로 놓은 셈이다.

실제 하마돈의 기술 4칸은 채용률 상위 4개로 이미 다 찬다.

```
지진 97.7%  ·  하품 96.3%  ·  스텔스록 92.5%  ·  날려버리기 62.3%
```

이 구성은 비행타입인 메가보만다에게 **데미지가 0** 이다. 승률 22% 가 아니라 100% 가 맞다.

그래서 지금은 **채용률 상위 4개를 '들고 다닐 법한 구성' 으로 보고 그 안에서 고른다.**

#### 그런데 이것도 정확하지는 않다

**채용률 상위 4개는 '각각 많이 쓰이는 4개' 지 '같이 쓰이는 4개' 가 아니다.**
실제로는 배분에 따라 구성이 갈린다.

> 한카리아스는 **AS형**(공격·스피드 투자)일 때 드래곤테일을 잘 안 들고,
> **HB형**(체력·방어 투자)일 때 스텔스록과 같이 드는 편이다.

사용률 데이터에는 **기술끼리의 조합 정보가 없다.** 스피드 분포에서 성격·노력치·도구를
독립으로 본 것과 똑같은 한계다. 로토덱스가 주지 않는 정보다.

| | 판단 |
|---|---|
| 채용률(마진)을 쓰는 것 | **충분히 쓸 만하다.** 4-C 는 이걸로 간다 |
| 형태별 기술 구성 | ~~직접 뛰면서 쌓아야 할 정보다. 지금 데이터로는 안 된다~~ |

> **아래 칸은 틀렸다. 1-A 에서 뒤집혔다.** 조합 정보가 통째로 없는 것은 맞지만,
> **노력치 채용률과 기술 채용률을 대조하면 상당 부분이 복원된다.** 한 판도 안 뛰고
> 나온다. 다음 절을 볼 것.

## 1-A. 형태를 가른다 — `forms.py`

### 왜 시작했나

"실전 기록을 수백 판 쌓아서 형태별 표본을 만들자" 고 잡았다가, 비용을 계산하고
접었다. 한 판 10분 · 한 판에 상대 3마리면, 한카리아스 **한 마리**의 형태별 분포를
보는 데만 70~100판, 12~17시간이다. 상위 20마리면 말이 안 된다.

> 그 시간의 산출물은 도구가 아니라 사람의 실력이다. — 사용자 지적, 2026-09-17

접고 나서 데이터를 다시 봤더니, **조합이 없다던 것이 틀렸다.**

| 포켓몬 | 노력치 A형 : C형 | 공격기 물리 : 특수 |
|---|---|---|
| 한카리아스 | 47 : 36 | 60 : 40 |
| 보만다 | 70 : 18 | 69 : 31 |
| 누리레느 | 0 : 34 | 30 : 70 |
| 하마돈 | 0 : 0 (전부 내구) | 100 : 0 |

기술의 물리/특수는 **때리는 능력치에 묶인 딱딱한 성질**이라, 노력치 배분과 대조하면
관계가 드러난다. 두 개의 마진을 교차시켜 조합을 되살린 것이다.

### 어떻게 만들었나

1. 배분을 **때리는 능력치 기준으로만** 가른다 — 물리형 / 특수형 / 양쪽형 / 내구형.
   (HB냐 HD냐는 안 따진다. 기술 선택을 가르는 것은 A·C 투자 여부다.)
2. 형태와 안 어울리는 기술의 **승산**에 `form_mismatch` 를 곱한다.
3. 갈라 놓고도 **섞으면 원래 채용률이 나오도록** 승산을 역산한다.
4. 거기에 더해 **어느 형태든 쓰는 칸수는 같게** 맞춘다 (누구나 기술칸 4개).

3번이 핵심이다. 갈라 놓기만 하면 원본을 망가뜨린 것이고, 원본을 지키면서 갈라야
데이터를 **해석**한 것이 된다. 재현 오차는 0.00%p 다 (`forms.mix_error`).

세로(채용률)와 가로(칸수) 두 조건을 번갈아 맞추는 방식이고, 각각 단조라서
이분법으로 정확히 잡힌다.

### 한 번 틀렸다가 고친 것 — 드래곤테일

처음에는 물리기를 전부 물리형 쪽으로 몰았다. 그랬더니 사용자가 든 바로 그 예시에서
**거꾸로** 나왔다.

    드래곤테일   물리형 40%   특수형 10%   내구형 24%   ← 실제와 반대

원인은 **위력 60짜리를 데미지 때문에 드는 게 아니라 강제 교체 때문에 든다**는 것이다.
공격 투자와 상관이 없다. 설명문에 "랜덤한 포켓몬으로 교체시킨다" 가 적힌 기술은
형태로 안 가르도록 고쳤다. 지금은 27 / 25 / 29 로 중립이다.

> 데미지 계산 밖에서도 **기술을 드는 이유**를 봐야 한다는 사례다.

### 진짜 수확 — 본 것이 안 본 것을 움직인다

형태별 확률이 생기면 베이즈를 거꾸로 쓸 수 있다.

    [용성군을 봤다]
      형태     물리형 47% -> 23%   특수형 36% -> 59%
      지진     67.0% -> 56.8%  ↓
      화염방사 27.3% -> 35.4%  ↑
      역린     25.7% -> 18.0%  ↓

전에는 **본 기술 하나만 100% 가 되고 나머지는 그대로**였다. 이제 하나를 보면
안 본 기술 일곱 개가 같이 움직인다. 상위 30마리 중 **8마리가 뚜렷하게 갈린다**
(5마리는 형태가 하나뿐이라 원래 갈릴 것이 없다).

**상대의 노력치 배분은 대전 시작 때 공개되지 않는다.** 형태는 아는 값이 아니라
끝까지 추론 대상이다. 본 것이 없으면 원래 채용률 그대로 나온다.

### 값어치와 대가를 같이 잰다

    python sensitivity.py --형태

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 최대 흔들림 |
|---|---|---|
| 형태를 더 믿는다 0.15 → 0.05 | 0 / 4 | 8.0%p |
| **형태를 덜 믿는다 0.15 → 0.40** | **1 / 4** | 6.0%p |
| **아예 안 가른다 0.15 → 1.0 (1-A 이전)** | **1 / 4** | 3.3%p |

- **1-A 는 장식이 아니다.** 안 가르던 때로 되돌리면 4개 중 1개에서 추천이 바뀐다.
- **대신 확인 안 되는 가정값이 하나 늘었다.** 0.15 냐 0.40 이냐로도 1개가 바뀐다.

`form_mismatch` 는 사용률만으로는 **원리상 확인이 안 된다** — 조합 정보가 없기
때문이다. 확인하려면 형태와 기술이 같이 적힌 표본이 필요하다. 즉 **구축기사**다.

### 이어서 — 성격과 도구도 형태에 딸린다

"경향도 강하면 확률이니 믿는 게 승률에 낫지 않나" 는 지적을 받고 다시 생각했다.
맞는 말이고, **내가 그은 선이 틀렸다.** 기준은 "규칙이냐 경향이냐" 가 아니라
**"잰 것이냐 지어낸 것이냐"** 여야 한다.

1-A 도 규칙만으로 된 게 아니다. 규칙은 **방향**만 줬고(물리기는 공격으로 때린다),
세기 0.15 는 가정이었다. 도구를 거부한 진짜 이유는 경향이라서가 아니라
**방향조차 내 감이었기 때문**이다. 그 방향은 잴 수 있었는데 안 재 보고 거부했다.

#### 근거의 등급을 나눠서 붙였다

| | 무엇이 방향을 정하나 | 등급 |
|---|---|---|
| 기술 ↔ 형태 | "물리기는 공격으로 때린다" | **게임 규칙** |
| 성격 ↔ 형태 | "자기가 때리는 능력치를 깎는 성격은 안 쓴다" | **게임 규칙** |
| 도구 ↔ 형태 | 263마리로 잰 포켓몬끼리의 상관 | **측정한 경향** |
| 메가스톤 ↔ 형태 | 메가 폼의 종족값 | **게임 데이터** |

#### 도구에는 규칙이 없다 — 본편 감각으로 갔으면 헛짚었다

본편이라면 구애머리띠(물리 확정)·구애안경(특수 확정)·돌격조끼(변화기 불가)가
형태를 확정 짓는다. **챔피언스에는 셋 다 없다.** 도구 166종을 뒤져서 확인했다.
남는 것은 힘의머리띠·박식안경 둘뿐인데 1.1배짜리고, 상위 20마리 채용률이 **0.0%** 다.

상위 20마리 도구 채용률을 갈라 보면 — 메가스톤 25.8% / 형태 확정 도구 0.0% /
나머지 74.1%.

그래서 감이 아니라 데이터에서 쟀다.

    먹다남은음식  내구형 +0.69   스피드 -0.59
    울퉁불퉁멧    내구형 +0.62   스피드 -0.54
    구애스카프    스피드 +0.58   내구형 -0.41
    생명의구슬    내구형 -0.43   물리형 +0.28
    풍선         내구형 +0.03   ← 아무 경향 없음

마지막 줄이 중요하다. **이 측정은 아무거나 다 맞다고 해 주지 않는다.**
풍선은 '땅 기술 무효' 라 뭔가 있을 것 같지만 재 보면 없다.

> ! 이건 **포켓몬끼리의 상관**이지 한 포켓몬 안의 상관이 아니다.
> "내구형 포켓몬이 먹다남은음식을 쓴다" 는 잰 것이고, "이 한카리아스가 HB 배분일
> 때 먹다남은음식을 쓴다" 는 가정이다. 생태학적 오류라고 부르는 함정이다.
> 다만 방향은 데이터가 정했고, 세기는 CONFIG 에 있고, 섞으면 원래 도구 채용률이
> 그대로 나오므로 틀려도 피해가 갇힌다.

메가스톤만 따로 다룬다. **메가스톤은 한 포켓몬만 쓰므로 포켓몬끼리 비교가 안 된다.**
대신 메가 폼의 종족값이 있다. 임계값을 두지 않고 **차이를 증거의 세기로** 쓴다.
그래서 한카리아스나이트Z(130/141, 차이 11)는 저절로 거의 안 움직이고,
메가루카리오Z(100/164, 차이 64)는 세게 움직인다.

#### 형태에 스피드 축을 넣었다

도구 경향을 재고 나서 알았다. **제일 센 축이 물리/특수가 아니라 내구 ↔ 스피드다.**
A/C 만 보면 그 축이 통째로 안 보인다. 그래서 형태를 AS / A / CS / C / 내구 로 늘렸다.
사용자가 처음부터 쓰던 "AS형태" "HB형태" 라는 표기에 이미 S 가 들어 있었는데
내 형태에는 없었다.

기술은 스피드 축을 안 본다 (`attack_part`). AS형과 A형은 같은 기술을 든다.

#### 고친 결과

| | 전 | 후 |
|---|---|---|
| 자기 공격력을 깎는 성격을 든 상대 | 24.2% | **3.8%** |
| 메가 종족값과 반대쪽에 투자한 상대 | 9.4% | **7.3%** |

성격·도구는 기술과 달리 **하나만 고르는 것**이라 같은 식을 못 쓴다.
각 형태의 확률 합이 1 이어야 하므로 표 맞추기로 푼다 (`_fit_categorical`).
섞음 오차는 성격·도구 모두 0.00%p 다.

#### 값어치 — 밀어붙인 쪽이 제일 약했다

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 최대 흔들림 |
|---|---|---|
| **기술을 형태로 안 가른다 (1-A 이전)** | **1 / 4** | **11.3%p** |
| 성격을 형태로 안 가른다 | 1 / 4 | 4.7%p |
| 메가 종족값을 안 쓴다 | 0 / 4 | 2.7%p |
| **도구 경향을 안 쓴다** | **0 / 4** | **2.0%p** |

기술↔형태가 압도적이고, **논쟁의 출발점이던 도구 경향이 제일 약하다.**
넣어서 손해는 없지만 여기부터 다듬을 이유는 없다.

### 남은 것

| | 상태 |
|---|---|
| 형태 ↔ 기술 | **됨** |
| 형태 ↔ 성격 | **됨** (규칙) |
| 형태 ↔ 도구 | **됨** (측정한 경향 + 메가는 종족값) |
| 변화기가 어느 형태에 붙나 | 약하게만 잡힌다. 칸수 보존으로 내구형에 조금 쏠릴 뿐이다 |
| 기술끼리의 조합 | 안 됨. 스텔스록과 드래곤테일을 **같이** 드는지는 데이터에 없다 |
| 가정값 4개의 **세기** | 안 됨. 방향은 규칙·측정이 정했지만 세기는 확인이 안 된다 |

마지막 세 줄은 **1-B(구축기사 샘플)** 로만 메워진다.

## 1-C. 기술 구성 갈래 — `combos.py`

1-B 로 표본을 모아 놓고 **가정값 네 개를 맞추는 데만** 썼다. 조합은 재 놓고
안 쓰고 있었다. 그걸 실제로 써먹는 자리다.

### 고친 것 1 — 사용률 목록 밖의 기술

사용률 자료에는 포켓몬마다 기술 **상위 10개**만 있다. 표본을 세 보니
한카리아스가 실제로 쓴 기술 456회 중 목록 안이 **323회(71%)** 뿐이었다.

    목록 밖인데 많이 쓰인 것: 칼춤 25 · 압정뿌리기 22 · 불꽃엄니 17 · 독찌르기 15

즉 **칼춤 한카리아스는 모델에서 확률이 0 이었다.** 나올 수가 없었다.
실제로는 랭커 표본의 22% 가 들고 있다. 이건 근사가 아니라 구멍이다.

확률을 얼마나 줘야 하는지는 **사용률이 답을 알고 있다.** 상위 10개 채용률
합이 298% 이고 기술칸은 4개(400%)다. 차이인 **102% 가 목록 밖 기술들의 몫**이다.
**얼마인지는 사용률이, 누구에게 줄지는 표본이** 알려 준다.

표본의 목록 밖 비율 117% vs 사용률이 남긴 예산 102% — 15% 안에서 맞는다.
따로 구한 두 숫자가 맞아떨어지는 것이 이 방법의 근거다.

### 고친 것 2 — 기술끼리의 조합

쌍을 하나하나 넣는 대신 **갈래**로 본다. 실제 구성이 두세 갈래로 뭉쳐 있기
때문이다. 표본에서 베르누이 혼합을 EM 으로 맞추고, 갈래 개수는 BIC 로 고른다
(많을수록 잘 맞지만 벌점이 있다). 한카리아스는 3개가 뽑혔다.

    1번 (54%)  역린 + 화염방사 + 칼춤
    2번 ( 7%)  파워젬 + 대지의힘 + 용성군
    3번 (39%)  스텔스록 + 드래곤테일 + 압정뿌리기

    스텔스록   1번  5%   2번  0%   3번 94%
    드래곤테일 1번  0%   2번  0%   3번 68%
    역린       1번 48%   2번  0%   3번  0%

EM 초기값을 난수로 두면 돌릴 때마 답이 바뀐다. **제일 멀리 떨어진 표본들**을
씨앗으로 써서 같은 답이 나오게 했다.

### 두 번 틀렸고 두 번 고쳤다

**첫 번째 — 갈래가 1-A 를 대체해 버렸다.**
갈래만 쓰면 1번에 역린과 화염방사가 같이 들어 있어서, 역린을 봐도 "1번"
까지만 알고 AS/CS 구분이 흐려진다. 실제로 **역린을 봤는데 CS형이 4% 에서
33% 로 올라갔다** — 1-A 혼자일 때가 더 맞았다.

둘은 서로 다른 것을 아는 신호다.

| | 무엇을 아나 | 믿을 근거 |
|---|---|---|
| 1-A | 물리기는 공격으로 때린다 | **게임 규칙** — 표본 수와 무관하게 맞다 |
| 1-C | 실제 구성은 몇 갈래로 뭉친다 | **표본**에서만 알 수 있다 |

그래서 대체하지 않고 **승산에서 곱했다.** 칸을 (형태 × 갈래) 로 펴고
섞으면 사용률이 나오도록 한 번에 맞춘다.

    승산(형태 f, 갈래 a, 기술 m) = κ_1A(f,m) × κ_갈래(a,m) × t_m
    Σ_f Σ_a P(f)P(a|f) p(f,a,m) = 사용률(m)     <- t_m 을 이걸로 역산

**두 번째 — 갈래 비중에 없는 마진을 맞추려 했다.**
"섞으면 갈래 비중이 나오도록" 맞췄더니, 1번 비중 54% 가 AS형 47% 보다 커서
**남는 몫이 CS형으로 밀렸다.** 특수형인데 역린·칼춤을 든 한카리아스가 나왔다.

원인은 간단했다. **갈래 비중에는 맞출 마진이 없다.** 갈래는 관측된 값이
아니라 표본에서 찾아낸 잠재 변수다. 맞춰야 하는 마진은 두 개뿐이다 —
**노력치(사용률)와 기술(사용률).** 노력치는 각 형태에서 갈래 확률의 합이
1 이면 저절로 지켜지고, 기술은 승산으로 맞춘다.

고친 뒤 (형태 → 갈래) 가 깨끗하게 갈렸다.

    AS형   -> 1번 68%  2번  0%  3번 31%
    CS형   -> 1번  3%  2번 95%  3번  2%
    내구형 -> 1번  5%  2번  2%  3번 93%

### 얻은 것 — 본 것 하나가 훨씬 많이 말해 준다

| 본 것 | 1-A 만 | 1-A × 1-C |
|---|---|---|
| 스텔스록 | 내구형 19% | 내구형 **38%** |
| 드래곤테일 + 스텔스록 | 내구형 22% | 내구형 **53%** |
| 역린 | AS형 84% | AS형 **95%** |
| 용성군 | CS형 69% | CS형 **99%** |
| 칼춤 | *보이지도 않음* | AS형 **82%** |

마지막 줄이 1-C 의 값어치다. 칼춤은 사용률 목록에 없어서 **1-A 는 그 기술이
있다는 것조차 몰랐다.**

### 얇은 칸을 어떻게 다뤘나

한카리아스 CS형 표본이 20마리인데 거기서 (형태 × 갈래) 아홉 칸을 추정하면
튄다. 그래서 **1-A 를 사전분포로 깔았다.** 갈래의 기술 profile 이 그 형태의
profile 아래에서 얼마나 그럴듯한지를 교차엔트로피로 재서 사전 쏠림으로 쓰고,
표본은 **칸이 두꺼운 만큼만** 그 위에 얹는다 (수축, 15마리쯤에서 반반).

### 지금 어디까지 붙었나

표본 25마리를 넘긴 **15종**이다. 나머지는 1-A 로 돌아간다 (갈래 없이 형태만).
전체 파이프라인 재현 오차는 0.5~1.3%p 로 표본 잡음 수준이고,
표 자체의 오차는 0.00%p 다. **표본이 늘면 저절로 늘어난다.**

## 1-B. 구축기사 표본 — `samples.py`

### 어디서 못 가져오고 어디서 가져왔나

사용자가 처음 준 곳은 champs.pokedb.tokyo (사용률과 같은 출처) 인데,
**이 작업 환경에서는 접근이 막힌다.** robots.txt 까지 403 이고 프록시 문제가
아니다. 나가는 IP 가 `160.79.106.x / AS396982 Google LLC` — 클라우드
데이터센터라 통째로 차단된다. 기기(아이패드/컴퓨터)나 와이파이와는 무관하고,
**로컬 실행이냐 클라우드 실행이냐**의 문제다. 집 회선에서 돌리면 열린다.

그 뒤 사용자가 개인 블로그 기사 주소 9개를 줬는데 **전부 열렸다.**
다만 사이트마다 사정이 달랐다.

| 사이트 | 데이터 형태 | 자동 수집 |
|---|---|---|
| **pokesol.app** | 본문 HTML 에 기계가 읽는 카드 | **된다** |
| 하테나블로그 (5편) | 배분이 스크린샷 안 | 이미지를 직접 봐야 함 |
| note.com · 네이버 | 스크린샷 안 | 〃 |

이미지 기사도 읽을 수는 있다. 게임의 「能力」 탭과 「ステータス」 탭 두 장이면
이름·특성·도구·기술·노력치가 다 나온다. 실제로 읽어서 확인했다.
다만 130편이면 260장이라 현실적이지 않아서 pokesol 쪽을 주력으로 썼다.

### pokesol 은 기계가 읽을 수 있었다

    <div data-type="pokemon-card" data-pokemon-id="823" data-nature-id="6"
         data-ability-ids="[46]" data-item-id="59" data-move-ids="[413,...]"
         data-evs="{hp:32,attack:0,defense:25,specialAttack:0,
                    specialDefense:7,speed:2}">

노력치가 정확한 숫자로 들어 있다 (합 66). 사람이 옮겨 적을 필요가 없다.

가져오는 길에 세 번 막혔고 세 번 고쳤다.

1. **본문이 HTML 에 없다.** React Router 라 `.data` 경로로 따로 온다.
   그 형식(turbo-stream)은 값을 납작하게 펴 놓고 번호로 서로 가리킨다.
2. **머리에 글자가 붙은 배열**이 섞여 있다. `["D", 1789554238536]` 은 날짜고
   `["M", ...]` 은 Map 이다. 번호로 착각해서 통째로 터졌다.
3. **목록 페이지가 없다.** robots.txt 를 보니 기사 페이지를 허용하면서
   **사이트맵을 안내**하고 있었다. 긁는 대신 그쪽을 썼다 (기사 3,452편).
   gzip 을 켜서 받으면 850KB 가 176KB 가 된다 — 남의 서버 대역폭이다.

### 일본어를 그대로 받는다

기사는 일본어다. 게임 파일에 두 언어가 같은 번호로 들어 있으므로
`build_names.py` 로 이름표를 만든다 — 포켓몬 270 · 기술 512 · 도구 166 ·
특성 217 · 성격 25. GitHub 쪽(projectpokemon/champout)은 접근이 된다.

못 알아들은 이름은 **조용히 버리지 않고 전부 보고한다.** 이름 하나를 놓치면
그 개체가 통째로 빠지는데, 그게 소리 없이 일어나면 표본이 조용히 편향된다.

### 세기를 맞추는 방법

표본 하나가 **형태와 기술·성격·도구가 같이 적힌 한 덩어리**다. 그러니
"이 세기였다면 이 표본이 나올 법했나" 를 물을 수 있다 (최대가능도).

기술 쪽은 정확한 가능도가 아니라 **유사가능도**를 쓴다. 기술 4칸 중 사용률
상위 목록 밖의 기술이 섞여 있어 정확한 집합 확률을 못 매기기 때문이다.
목록에 있는 기술을 각각 독립 동전으로 보고 더한다. 세기 하나를 고르는
데는 이걸로 충분하다 — 아래에서 실제로 되찾아지는 것을 확인했다.

### 실제로 맞춘 값 — 내가 잡은 것이 전부 너무 약했다

개체 1,326마리로 맞췄다.

| 가정값 | 내가 감으로 | 표본이 고른 값 |
|---|---|---|
| `form_mismatch` | 0.15 | **0.05** |
| `nature_mismatch` | 0.05 | **0.01** (격자 바닥) |
| `item_tendency_strength` | 1.0 | **4.5** |
| `mega_stat_strength` | 1.5 | **1.5** — 맞았다 |

927마리에서 잰 값과 1,326마리에서 잰 값이 같아서 수렴한 것으로 본다.

성격이 바닥에 붙은 것은 격자를 더 넓히라는 뜻이 아니다 — **랭커는 자기
공격력을 깎는 성격을 아예 안 쓴다**는 뜻이다. 그래도 0 으로는 안 둔다.
확률이 0 이면 관찰이 어긋났을 때 사후확률이 통째로 무너진다.

### 맞춘 뒤에 다시 잰 감도 — 두 가지가 같이 좋아졌다

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 흔들림 |
|---|---|---|
| 기술을 형태로 안 가른다 (1-A 이전) | 0 / 4 | **18.0%p** |
| 성격을 형태로 안 가른다 | 0 / 4 | 9.3%p |
| 메가 종족값을 두 배로 | **1 / 4** | 6.7%p |
| 도구 경향을 안 쓴다 | 0 / 4 | 2.0%p |

- **1-A 의 값어치가 11.3%p → 18.0%p 로 올랐다.** 세기를 제대로 맞추니
  형태를 가르는 것이 더 크게 값을 한다.
- **추천이 흔들리는 대면이 1/4 → 0/4 로 줄었다.** "뭘 누를까" 의 답이
  가정값에 덜 매달리게 됐다.

### 기술끼리의 조합 — 마진으로는 원리상 못 얻는 것

한카리아스 114마리. 사용자가 처음 짚은 것이 그대로 나왔다.

    드래곤테일  스텔스록   같이 35  기대 19.3  리프트 1.81  <- 같이 든다
    스케일샷    칼춤      같이 17  기대  5.9  리프트 2.90  <- 같이 든다
    드래곤테일  역린      같이  1  기대  9.8  리프트 0.10  <- 서로 안 든다

두 갈래로 완전히 갈린다.
  유틸형  드래곤테일 + 스텔스록 + 압정뿌리기
  공격형  스케일샷 + 칼춤 + 역린

드래곤테일과 역린은 **둘 다 물리 드래곤 기술인데 114마리 중 딱 1번만** 같이
나왔다. 1-A 에서 드래곤테일을 '형태 중립' 으로 둔 것이 절반만 맞았다 —
형태로는 안 갈리는 게 맞지만 **다른 기술과의 관계로는 강하게 갈린다.**

> 리프트만으로 줄 세우면 안 된다. 드물게 나오는 기술 둘은 우연히 한 번도
> 안 겹칠 수 있고, 그러면 리프트 0.00 으로 제일 커 보인다. 처음에 그렇게
> 짰다가 표가 쓸모없어졌다. 지금은 기대값 2.0 이상인 쌍만 보고
> **기대값과 실제의 차이**로 줄 세운다.

### 조용히 새던 것들 — 전부 막고 보고하게 했다

표본을 다루면서 제일 무서운 것은 **소리 없이 빠지는 것**이다. 이름 하나를
못 읽으면 그 개체가 통째로 빠지고, 그게 조용히 일어나면 표본이 조용히
편향된다. 그래서 전부 보고하게 했다.

| 무엇 | 몇 건 | 어떻게 했나 |
|---|---|---|
| 폼 표기가 다름 (`イダイトウ(♂)`) | 41 | 사용률의 `nameJa` → **키**로 잇는 표를 만듦 |
| 전각/반각 (`メガリザードンＹ` vs `Y`) | — | 정규화 |
| 성별 기호 (`♂` vs `(オス)`) | 41 | 정규화 |
| 폼을 떼고 읽음 (`ギルガルド(盾)`) | 26 | 실드폼이 배틀 시작 폼이라 그대로 두되 보고 |
| **다른 게임 기사** (SV·ORAS) | 2편 | 포켓몬 절반이 도감에 없으면 통째로 버림 |
| 챔피언스에 없는 포켓몬 | 8 | 보고만 (`ミライドン`, `ハバタクカミ` 등) |

대쓰여너 ♂/♀ 는 공격이 112 vs 92, 특공이 80 vs 100 이다. 이름만으로 뭉개면
종족값이 20이나 틀린다. 41마리가 걸려 있었다.

**게시일도 조용히 새고 있었다.** `["D", 밀리초]` 로 온 것을 내가 버려서
161파티가 '시기 모름' 이 됐다. 제목에 시즌이 없는 기사가 많으니 게시일은
언제 것인지 아는 유일한 단서다. 사이트맵의 `lastmod` 로 전부 메웠다
(`python fetch_pokesol.py --날짜만`). 결과: 265파티 중 253파티가 2026-09.

> 이때 배운 것 하나. **수집이 도는 중에 코드를 고치면 돌던 쪽은 옛 코드를
> 쓴다.** 그래서 나중에 따로 메울 수 있는 길을 만들어 뒀다.

### 만들어 놓고 검증했다 — 정답을 아는 가짜 표본으로

자료가 없으니 **지금 모델로 가짜 표본을 만들어** 검증했다.
세기를 0.05 로 놓고 표본을 뽑은 뒤, 맞추기가 0.05 를 되찾는지 본다.

| 개체 수 | 세 번 재면 |
|---|---|
| 48마리 | 0.02 / 0.05 / 0.10 — 매번 다르다 |
| 200마리 | 0.05 / 0.10 / 0.05 — 대충 맞는다 |
| 800마리 | 0.05 / 0.05 / 0.05 — 확실하다 |

**한 편에 6마리이므로 35편이면 대충, 130편이면 확실하다.**
자료를 얼마나 모아야 하는지를 모으기 전에 알 수 있다.

기술 쌍(리프트)도 가짜 표본에서 확인했다. 용성군-역린이 0.50 으로
**서로 안 든다**가 잡힌다. 이건 마진으로는 절대 안 나오는 정보다.

### 기사마다 값어치를 다르게 본다 (사용자 요청)

champs.pokedb.tokyo 기사를 더 무겁게 본다. 그쪽은 순위 자료와 묶인 곳이고
사용률도 거기서 온다. pokesol 은 누구나 쓰는 메모장이라 `自分用メモ`,
`BW縛り` 같은 글도 섞인다. 실제로 모아 보니 **pokesol 기사의 74%가 제목에
순위가 없었다.**

| | 배율 |
|---|---|
| `champs.pokedb.tokyo` | 3.0배 |
| `pokesol.app` | 1.0배 |
| 순위를 안 밝힌 글 | ×0.5 |
| 최종 50위 이내 / 500위 이내 | ×2.0 / ×1.5 |

**이건 측정이 아니라 판단이다.** 그래서 숫자를 `SOURCE_WEIGHT` ·
`RANK_WEIGHT` 한 곳에 모으고 왜 그런지 코드에 적었다.

값어치를 매기는 것과 **마진을 갈아치우는 것은 다르다.** 여기서 하는 것은
"어느 표본을 더 믿을까" 이지 "래더 분포가 이렇다" 가 아니다.

### 섞지 않는 두 가지

- **시즌.** 사용자가 먼저 짚었다 — "시즌이 바뀌면서 메타가 바뀌니 참고용".
  시즌을 반드시 같이 받고 보고서에서 나눠 보여 준다.
- **랭커 편향.** 기사는 잘 나가는 구성 쪽으로 치우쳐 있다. 그래서 표본으로
  **마진을 갈아치우지 않는다.** 마진은 사용률 것을 쓰고 표본은 **조합만** 고친다.
  보고서에 표본 형태 분포와 사용률 형태 분포를 나란히 찍어서, 둘이 다른 것이
  오류가 아니라는 것을 눈으로 보게 했다.

그래서 상대 구성을 정하는 자리는 `forms.conditional_table` 과 `forms._pick_table`
두 곳에 몰려 있다. 형태별 자료가 생기면 여기만 갈아끼우면 된다.

### 함정 넷

1. **시뮬레이터 범위가 샌다.** 기술 512개를 다 구현하려 들면 끝이 없다.
   위에서 셌듯 **상위 20마리가 실제로 쓰는 기술은 97개**다.
   사용률은 "무엇을 계산하느냐" 뿐 아니라 **"무엇을 먼저 구현하느냐"까지 정해 준다.**

2. **조용히 틀리는 것.** 지금까지 이 프로젝트가 잘한 건 `!` 경고 문화다.
   턴 루프에서도 안 넣은 효과는 **반드시 시끄럽게** 알려야 한다.
   시뮬레이터 안에서 승률이 오르는 것은 아무것도 증명하지 않는다.

3. **6대6 감각으로 재는 것.** 기본 룰은 **6마리 파티 → 3마리 선출**이다.
   스텔스록처럼 "교체할 때마다 누적" 되는 것의 값어치를 본편 6대6 기준으로 재면
   과대평가가 된다. 반대로 강제 교체기는 3마리 기준에서 더 세다.

4. **균형 전략에 과투자.** 동시 수 완전해는 "상대도 완벽하다"는 가정인데,
   실제 상대는 사용률대로 움직인다. 5장 결론대로 **착취 쪽(4-C)이 싸고 세므로**,
   균형해는 필요해지면 그때 해도 늦지 않다.

### 지금 상태를 한 문장으로

> **"한 대 때리면 얼마 들어가나"는 믿을 만하고,
> "그래서 이 대면을 이기나"는 아직 반만 맞다.** 그 반을 채우는 것이 턴 루프다.

## 7단계에서 실제로 한 것 — `search.py`

```
python search.py 한카리아스,아머까오,누리레느 하마돈,타부자고,킬가르도 \
       --초 10 --기술 지진,역린,화염방사,칼춤 --봤다 자뭉열매
```

`battle.py` 는 **내가 수순을 미리 정해 주면** 그대로 돌려 본다
("역린 → 역린 → 역린 을 400판 돌려라"). 7단계는 반대다.
**이번 턴에 둘 수 있는 모든 수를 각각 끝까지 돌려 보고 제일 나은 것을
고른다.** 기술 4개 + 벤치로 교체 2개면 수가 6개다.

### 얼마나 깊이 보나 — 되도록 끝까지

사용자가 정했다: *"C로 하되 가능하면 끝까지 돌려보는게 좋아."*
그래서 기본이 끝까지다. 예산(초)이 모자랄 때만 이 순서로 줄인다.

1. **판수를 줄인다** (깊이는 그대로)
2. **가망 없는 수를 먼저 버린다** — 적은 판수로 한 바퀴 돌려 하위 절반을
   떨어뜨리고, 살아남은 수에 판수를 두 배로 준다. 마지막에는 후보 한둘이
   제일 많은 판수를 받는다
3. **그래도 모자라면** 몇 턴에서 끊고 판세로 점수를 매긴다 —
   **마지막 수단이고, 썼으면 보고서에 적는다**

### 양쪽 다 파티다 ★

**상대도 파티로 받는다.** 챔피언스는 6마리에서 3마리를 내는 룰이므로
상대도 보통 셋이다.

> **처음에는 상대를 한 마리만 받았다 (2026-09-19에 고침).** 사용자가
> 되물어서 잡혔다 — *"왜 내 파티는 6인이 아니며 상대는 1인이지?"*
> 상대 벤치가 계산에 아예 안 들어가서 **"지금 이놈을 잡는 수" 를
> "판을 이기는 수" 라고 답했다.**
>
> 아머까오가 나와 있는 같은 자리에서 재 봤다 (25초씩):
>
> | 수 | 상대 1마리 | 상대 3마리 |
> |---|---|---|
> | 한카리아스로 교체 | 97.6 | 63.7 |
> | 철벽 | 94.0 | 54.9 |
> | **누리레느로 교체** | **94.6 (2등)** | **30.5 (꼴찌)** |
>
> 수준이 내려간 것은 당연하다 — 상대가 셋이니 어렵다. 문제는
> **순위가 뒤집힌 것**이다. 64%p 차이다.
> `battle.py` 는 **처음부터 양쪽 파티를 받을 수 있었다.** 7단계만
> 한 마리로 좁혀 놓고 있었던 것이다.

**본 것은 그놈에게만 붙인다.** "지진을 봤다" 는 그때 나와 있던 놈이
지진을 쓴다는 뜻이지 벤치의 누리레느도 지진을 든다는 뜻이 아니다.
하나만 주면 **나와 있는 놈**에게만 붙고, 여럿에게 붙이려면
`{이름: 관찰}` 로 준다.

### 답을 아는 상황을 만들어 확인한다

**승률 숫자는 그럴듯하게 나오기 쉽다.** 그래서 "이건 무조건 이 수여야
한다" 는 자리를 만들어 놓고 거기서만 확인한다. 이 방식으로 **네 개**를
잡았다.

1. **`Policy` 가 내 기술을 몰래 바꿔 썼다.** 계획은 첫 턴 한 수뿐인데
   그 뒤부터 사용률 상위 기술을 꺼내 썼다. 땅 기술만 든 한카리아스가
   2턴째부터 화염방사를 쓰면서 아머까오(땅 무효)를 96.7%로 이겼다.
2. **점수가 "이기면 1.0" 이었다.** 3마리 다 살려 이긴 것과 두 마리를
   내주고 간신히 이긴 것이 같은 점수라, "이놈을 공짜로 잃어도 벤치가
   이기니 괜찮다" 는 수를 골랐다.
   → 이김 0.70~1.00 / 비김 0.35~0.50 / 짐 0.0 으로 가른다.
3. **상대가 한 마리뿐이었다** (위 참고).
4. **나와 있는 놈이 1번이 아니면 계획이 통째로 버려졌다.** `Policy` 가
   계획의 주인을 `party[0]` 으로 굳혀 놔서, 2번을 내보낸 채로 물으면
   `act` 첫 줄에서 걸러져 **그 수를 안 두고 답했다.** 같은 씨앗으로
   세 계획을 돌렸더니 결과가 글자까지 똑같았다:

   ```
   나와 있는 놈 = 2번 (아머까오)
       철벽       -> 이김  파티HP 81.04%  6턴
       브레이브버드  -> 이김  파티HP 81.04%  6턴
       날개쉬기     -> 이김  파티HP 81.04%  6턴
   ```

   그런데 화면 점수는 91.9~93.1 로 그럴듯하게 벌어져 있었다.
   **숫자만 봐서는 절대 못 잡는다.**
   → 계획의 주인을 손으로 적지 않고 `Battle` 에게 묻는다
   (`lead=b.me_party.active.base`).

**교훈 — 번호가 섞이는 자리는 전부 의심한다.** "나와 있는 놈이 몇
번인가", "쓰러진 놈을 빼면 번호가 밀린다" 같은 것은 틀려도 안 터지고
승률만 조금 이상해진다. 그래서 **번호를 손으로 적지 말고 객체에게
물어본다.**

> 시험을 만들 때도 미끄러졌다 — "땅 기술만 줬다" 면서 스톤에지를
> 끼워 넣어 시험 자체가 무의미했던 적이 있다.

### 예산 재기 — 첫 판으로 재면 안 된다

첫 판은 캐시(`rate_moves` · 도구 규칙 · 형태 모델)를 덥히느라
**461ms**, 더워진 뒤는 **2.1ms** 다. **220배**다. 덥히는 판을 3판으로
고정해 두고 재니 아직 차가운 값을 잡았고, 멀쩡한 판인데 "예산이
모자라다" 며 얕은 모드로 떨어졌다. **그런데 점수가 전부 100.00 으로
나와서 오히려 좋아 보였다.**

→ 덥히기를 **시간이 안정될 때까지**로 바꾸고, 평균이 아니라
**제일 빠른 판**으로 잰다 (평균은 아직 덜 더워진 판에 끌려간다).
예산 시계는 **재고 나서** 켠다.

## 실전 도구 — `live.py` (글자판) · `gui.py` (창)

계산이 아무리 맞아도 **사람이 게임하면서 못 쓰면 소용이 없다.**
챔피언스는 턴당 40초(보유 7분)이고, 사용자는 폰으로도 본다.

### 나누는 기준 — 계산은 창에 두지 않는다

| | 무엇을 하나 |
|---|---|
| `calc`·`battle`·`scout`·`search`·`pick` | 계산 |
| `live.py` | **창과 글자판이 같이 쓰는 규칙** + 글자판 화면 |
| `gui.py` | 창. 값을 모아 넘기고 결과를 찍기만 한다 |

**이 컨테이너에는 tkinter 도 화면도 없다.** 창은 여기서 볼 수가 없다.
그래서 **틀리면 조용히 틀어질 것은 전부 `live.py` 로 내려** 거기서
시험한다 — 고르는 규칙(`rank_hits`·`learnable`·`abilities_of`),
상대 목록 만들기(`turn_state`), 관찰 붙이기(`evidence_map`).

### 자리는 양쪽 다 6개

| | 자리 | 무엇을 적나 |
|---|---|---|
| 내 파티 | **6** | 능력치까지 전부 — **내 것이니까 안다** |
| 상대 | **6** | 이름 · 남은 HP · 나와 있나, **셋만** |

**상대에게는 배분·성격을 묻지 않는다.** 모르는 것이 맞고, 모르는 것을
사용률에서 뽑는 것이 이 프로그램이 하는 일이다. 칸을 만들어 두면
찍어서 채우게 되고, **그 찍은 값이 그대로 계산에 들어간다.**

> 반대로 **내 파티는 반드시 묻는다.** 처음에는 묻지도 않고 사용률 1위를
> 씌웠는데, 같은 아머까오라도 HB 장난꾸러기는 방어 172, HD 신중은 125 —
> **38% 차이**다. 이 정도면 "한 대 버티나" 가 뒤집힌다.

상대 HP 를 **0 으로 두면 쓰러진 것**으로 보고 계산에서 뺀다.
빼고 나면 번호가 밀리므로 **나와 있는 놈의 번호를 다시 찾아야 한다** —
`live.turn_state` 가 한 군데서 한다.

### 여기서 잡은 것 — 전부 화면에는 멀쩡해 보였다

1. **남은 HP 를 아예 못 받고 있었다.** `Side` 가 늘 만피에서 시작했다.
   3턴만 지나도 양쪽 다 깎여 있는데, 그러면 "지금 이 상황" 이 아니라
   **"처음이었다면"** 을 재게 된다.
2. **`적55` 가 화면에만 찍히고 계산에 안 들어갔다.** `state()` 가 상대
   HP 를 안 넘겼다.
3. **매 세션 첫 턴이 몰래 얕은 모드로 돌았다** (위 7단계 참고).
4. **창 코드가 문법 말고는 한 줄도 안 돌아간 채로 윈도우에 갔다.**
   그래서 윈도우에서만 네 번 터졌다 (한글 출력 · 한글 입력 등).
   → `faketk/tkinter.py` — **가짜 tkinter.** `PYTHONPATH` 앞에 두면
   창을 그리지 않고 `gui.py` 를 통째로 돌린다. 칸 채우고, 단추 누르고,
   추천·선출이 나오는 데까지 간다. 붙이자마자 점검 코드의 결함을
   하나 잡았다 (엿보기가 너무 일찍 풀려 두 번째 검사가 첫 번째 값을
   다시 보고 있었다).
   **잡는 것**: 오타 · 없는 메서드 · 인자 개수 · 칸에 넣은 값이
   계산까지 가는가. **못 잡는 것**: 생김새 · 글꼴 · 진짜 위젯 ·
   윈도우 인코딩. 그래서 **윈도우 빌드의 진짜 `--점검` 을 없애지 않는다.**
