# pokemon_Ai

포켓몬 챔피언스의 전투 방식을 코드로 옮기고, 그 위에서 **"지금 이 상황에서 무엇이 최선의 수인가"** 를 알려주는 도구를 만드는 프로젝트.

그래픽은 구현하지 않는다. 전투 규칙과 계산만 다룬다.

## 계산기 쓰는 법

```
python calc.py 메가보만다 이판사판태클 하마돈
```

이름만 넣으면 **실전에서 제일 많이 쓰는 성격·노력치·도구**를 자동으로 적용해서 계산한다.
그냥 `python calc.py` 만 치면 하나씩 물어보는 방식으로 쓸 수 있다.

나오는 결과는 이렇다.

```
  메가보만다  →  하마돈
  기술: 이판사판태클 (노말→비행 물리 위력144)
  상성: 보통  /  자속 있음
  공격 216  vs  방어 151   상대 HP 215

  데미지  117 ~ 138   (HP의 54.4% ~ 64.2%)
  결론    확정 2타
  · 스카이스킨: 노말 → 비행, 위력 1.2배
  급소면  175 ~ 207   (81.4% ~ 96.3%)  →  확정 2타
```

계산을 고쳤으면 `python tests.py` 를 돌려서 깨진 데가 없는지 확인한다.

> 이름만 넣었을 때 **1위 도구가 메가스톤이면 메가로 계산한다.** 사용률은 기본 폼 기준으로
> 집계되고 메가는 '도구 채용률'로만 나타나기 때문이다 (보만다나이트 97.7% → 메가보만다).
> 채용률이 낮으면(한카리아스나이트Z 35.3%) 그 숫자를 같이 적어 준다.

## 최선수 추천 쓰는 법

```
python best.py 메가보만다 하마돈
python best.py 메가보만다 하마돈 이판사판태클 지진 용의춤
```

기술을 직접 적으면 그것만 비교하고, 안 적으면 사용률 상위 기술을 대신 쓴다.
`--트릭룸` 을 붙이면 느린 쪽이 먼저 움직이는 것으로 본다.

나오는 것은 세 덩어리다.

**1. 스피드 비교** — 내가 먼저 때리는가. 상대 배분은 모르므로 사용률로
**"상대 스피드가 얼마일 수 있는지"와 "내가 더 빠를 확률"**까지 같이 낸다.

```
[스피드]  나 172  vs  상대 288   →  상대가 먼저 때린다
  상대 배분은 사실 모른다. 사용률로 보면 상대 스피드는 143 ~ 288 사이다.
    내가 더 빠를 확률  약 0.6%
    · 구애스카프 61.3% → 스피드 214 ~ 288  (이 경우 내가 후공)
    · 스피드 도구 없음 38.7% → 스피드 143 ~ 192
```

**2. 기술 일괄 비교** — 내 기술과 상대 기술을 각각 표로. 데미지·명중률·확정 몇 타와
'이번 턴에 쓰러뜨릴 확률'(명중률까지 곱한 값)이 붙는다.

**3. 대면 결론** — 이 대면을 이기는가.

```
[대면 결론]
  추천 기술   이판사판태클   (확실히 이김)
    · 내가 먼저 때린다  (스피드 172 vs 67)
    · 내가 상대를 쓰러뜨리는 데 2번 (확정)
    · 상대의 제일 아픈 수 '얼음엄니' 로는 나를 쓰러뜨리는 데 2번 (확정)
    · 상대 기술 중 나에게 아예 안 통하는 것 — 지진(97.7%), 땅가르기(0.5%)
    ! 이판사판태클: 준 데미지의 1/3 를 자신도 받는다
```

선공이면 같은 타수라도 이기고, 후공이면 한 번 더 빨라야 이긴다.
난수 폭까지 보고 **확실히 이김 / 난수 싸움 / 확실히 짐** 으로 가른다.
**추천 기술은 데미지가 제일 센 것이 아니라 대면을 이기는 것으로 고른다.**

`!` 가 붙은 기술은 위력 숫자만으로는 안 되는 기술이다 (공격기 335개 중 55개).
2턴 기술·연속 히트·고정 데미지·위력 가변·반동·날씨 의존을 게임 설명문에서 찾아낸 것이다.
**배율을 찍어 넣지는 않는다.** 아는 척해서 틀린 값을 넣느니 모른다고 말하는 편이 낫다.

아직 못 하는 것: 변화기의 값어치(4-B) · 급소 · 교체 · 날씨/필드 ·
선제공격기에 붙은 조건(만나자마자는 나온 첫 턴만).

## 여러 턴 돌려보기

```
python battle.py 메가보만다 하마돈
python battle.py 메가보만다 하마돈 --기록      한 판을 턴별로 찍어 본다
```

`best.py` 는 한 턴만 본다. 그래서 데미지가 0인 기술(용의춤·날개쉬기·칼춤)에는
점수를 못 매긴다. 이건 턴을 끝까지 돌려서 답을 낸다.

```
  계획                              승률    이겼을 때 남는 HP   남는 랭크           남는 몸
  용의춤 → 용의춤 → 이판사판태클    100.0%  38%                 공격+2 스피드+2     98
  역린                              100.0%  89%                 없음                89
```

**내놓는 답이 승패가 아니라 '끝났을 때의 상태' 다.** 승률이 같아도 남는 몸이 다르다.
쌓아둔 랭크는 상대가 쓰러져도 남아서 **후속 포켓몬까지 따라가기 때문**이다.

반영한 것 — 변화기 효과(설명문에서 읽어낸다), 날씨·필드(하마돈 모래날림 99.8% 등
등장만으로 까는 특성 포함), 1회용 도구(자뭉열매·기합의띠·먹다남은음식),
턴이 있어야 되는 특성(따라큐 「탈」, 브리두라스 「지구력」, 한카리아스 「까칠한피부」,
드닐레이브 「열교환」, 「옹골참」), 명중률·급소·반동,
그리고 상태 이상 — 화상·마비·독·맹독(누적)·잠듦·졸음(하품)·얼음·혼란.

> 상태이상 면역은 출처가 갈린다. **특성 면역 9개와 기술별 타입 면역 4개는 게임
> 설명문에 적혀 있어서 읽어 쓴다.** 반면 '불꽃타입은 화상에 안 걸린다' 같은
> 타입 자체의 면역은 게임 데이터 어디에도 없어서 본편 규칙을 가정했고,
> 걸릴 때마다 경고가 뜬다. 참고로 `잠자기` 는 게임 설명문이 **2턴**이라
> 본편(3턴)과 다르다 — 게임 쪽을 따랐다.

> 상대 기술은 **채용률 상위 4개**를 들고 있다고 본다. 이건 '각각 많이 쓰이는 4개' 지
> '같이 쓰이는 4개' 가 아니다 (한카리아스는 AS형이면 드래곤테일을 잘 안 든다).
> 형태별 구성은 직접 뛰면서 쌓아야 할 정보다. 자세한 것은
> [docs/ai-design.md](docs/ai-design.md) 6장.

## 교체가 있는 대전 (3대3)

```
python battle.py 메가보만다,아머까오,고릴타 브리두라스,하마돈,한카리아스
```

쉼표로 여러 마리를 적으면 교체가 있는 대전이 된다. 전에는 "확실히 짐" 하나뿐이던
대면에서 **빠지는 것이 선택지로 올라온다.**

```
계획                              승률
지진                              45.5%
고릴타 로 교체 → 10만마력         39.5%   ← 전에는 이 답을 표현조차 못 했다
```

**빼는 것과 내주는 것은 값이 다르다.** 불리하다고 늘 빼는 게 답은 아니다.

| | 치르는 값 | 얻는 것 |
|---|---|---|
| **뺀다** | 들어오는 놈이 **그 턴에 한 대 맞는다** + 압정 | 뺀 놈이 살아남는다 |
| **내준다** | 한 마리를 잃는다 | 다음 놈이 **공짜로** 나온다 (그 턴에 안 맞는다) |

```
계획                       승률    이길 때 잃는 마릿수   남는 파티 HP
지진 (버틴다)              19.3%   1.66마리              25%
고릴타 로 교체             10.0%   2.00마리              17%   ← 빼는 쪽이 더 나쁘다
```

그래서 승률만 보지 않고 **'이길 때 몇 마리를 잃었나'** 까지 같이 센다.

그리고 **누구를 내보낼지는 HP 로 정하지 않는다.** 필요한 HP 는 상대마다 다르기 때문이다.

```
상대: 브리두라스
  따라큐(HP 30%)      2.09   ← 탈로 한 대 막고 야습(우선도 +1)으로 때린다
  킬라플로르(HP 100%)  2.30
  누리레느(HP 100%)    0.81   ← HP 로 골랐으면 이놈이 1순위였다
```

"이 상대를 상대하려면 몇 대를 버텨야 하고, 지금 HP 로 그게 되는가" 를 잰다.

**물러나면 랭크가 사라진다.** 그래서 용의춤을 쌓았으면 안 빠져야 하고,
상위권이 날려버리기·울부짖기를 드는 이유(상대가 쌓은 것을 통째로 날린다)도 계산으로 나온다.

압정 4종(스텔스록·압정뿌리기·독압정·끈적끈적네트), 떠 있으면 압정을 안 밟는 규칙,
독타입이 독압정을 걷어 가는 것, 위협(보만다 99.3%)까지 들어있다.

> 압정 수치는 게임 데이터에 없다. 설명문이 "상대 필드를 스텔스록 상태로 만든다" 뿐이라
> 본편 값을 가정했고 결과에 경고가 뜬다.

## 상대를 분포로 보기

```
python battle.py 메가보만다 하마돈 --분포
python battle.py 메가보만다 하마돈 --분포 --봤다 얼음엄니
```

상대가 뭘 들고 있는지는 모른다. 대신 **사용률이 있다.** 매 판 상대를 채용률대로
새로 뽑아서 싸우므로, 나오는 승률이 '실제로 만날 상대들을 평균한 값' 이 된다.

제일 쓸모 있는 건 이 부분이다.

```
[졌을 때 상대는 이랬다]
  · 기술 '얼음엄니' — 졌을 때 100% 에 있었다 (평소 5%, 21.4배)
```

평소 잘 안 나오는 것이 위에 뜨면 **운 나쁘면 지는** 경우이고,
자주 나오는 것이 뜨면 **진짜로 불리한** 대면이다.

`--봤다` 로 실제로 본 기술을 넣으면 확률이 100%로 고정돼서 범위가 좁아진다.

```
아무것도 모를 때     승률 96.3%
얼음엄니를 봤을 때   승률 20.4%
```

> 기술 채용률의 합이 포켓몬마다 평균 **376%** 다. 기술칸이 4개이므로 채용률을
> '그 칸에 들어 있을 확률' 로 그대로 쓸 수 있다는 뜻이다. 다만 칸 수 제약 때문에
> 그냥 뽑으면 어긋나서, 조건부로 직접 뽑는다 (재현 오차 1.1%p).

### 기술끼리의 조합 — 마진으로는 원리상 안 나오는 것

```
python samples.py --쌍 한카리아스
```

한카리아스 114마리 표본. 사용자가 처음 짚은 것이 그대로 나왔다.

| 기술 A | 기술 B | 같이 | 기대 | 리프트 | |
|---|---|---|---|---|---|
| **드래곤테일** | **스텔스록** | 35 | 19.3 | **1.81** | ← 같이 든다 |
| 드래곤테일 | 압정뿌리기 | 18 | 8.3 | 2.18 | ← 같이 든다 |
| 스케일샷 | 칼춤 | 17 | 5.9 | **2.90** | ← 같이 든다 |
| **드래곤테일** | **역린** | 1 | 9.8 | **0.10** | ← 서로 안 든다 |
| 드래곤테일 | 칼춤 | 1 | 7.5 | 0.13 | ← 서로 안 든다 |

**두 갈래로 완전히 갈린다.**

- 유틸형 — 드래곤테일 + 스텔스록 + 압정뿌리기
- 공격형 — 스케일샷 + 칼춤 + 역린

드래곤테일과 역린은 **둘 다 물리 드래곤 기술인데 114마리 중 딱 1번만 같이
나왔다** (따로따로였다면 9.8번). 1-A 에서 드래곤테일을 '형태 중립' 으로 둔 것이
절반만 맞았다 — 형태(A·C 투자)로는 안 갈리는 게 맞지만 **다른 기술과의 관계로는
강하게 갈린다.**

> 리프트만으로 줄 세우면 안 된다. 드물게 나오는 기술 둘은 **우연히** 한 번도 안
> 겹칠 수 있고 그러면 리프트가 0.00 으로 제일 커 보인다. 처음에 그렇게 짰다가
> 표가 쓸모없어졌다. 지금은 '따로따로였다면 몇 번은 겹쳤어야 하는 쌍' 만 보고
> **기대값과 실제의 차이**로 줄 세운다.

## 형태를 가른다 (1-A)

```
python forms.py 한카리아스
python forms.py 한카리아스 --봤다 용성군
python forms.py                          # 상위 30마리 중 어디서 갈리는지
```

위의 분포에는 구멍이 하나 있었다. 기술을 **서로 독립**이라고 보고 뽑아서,
*AS형인데 용성군을 든 한카리아스* 가 태연히 나왔다. 그런 건 없다.

조합 정보가 사용률에 없다고 적어 뒀었는데, **그게 틀렸다.**
노력치 배분 채용률과 기술 채용률을 대조하면 관계가 드러난다.

| 포켓몬 | 노력치 A형 : C형 | 공격기 물리 : 특수 |
|---|---|---|
| 한카리아스 | 47 : 36 | 60 : 40 |
| 보만다 | 70 : 18 | 69 : 31 |
| 누리레느 | 0 : 34 | 30 : 70 |
| 하마돈 | 0 : 0 (전부 내구) | 100 : 0 |

거의 맞아떨어진다. 그래서 배분을 **때리는 능력치 기준으로만** 가르고
(물리형·특수형·양쪽형·내구형), 형태와 안 어울리는 기술의 승산을 깎는다.

**중요한 건 그다음이다.** 갈라 놓고도 **섞으면 원래 채용률이 그대로 나오도록**
승산을 역산한다. 안 그러면 데이터를 해석한 게 아니라 망가뜨린 것이다.
재현 오차는 0.00%p 다.

```
  기술            전체     AS형     CS형     내구형
  지진            67.0%    85%      42%      70%   ← 형태로 갈린다
  용성군          30.1%    14%      50%      32%   ← 형태로 갈린다
  역린            25.7%    40%      8%       22%   ← 형태로 갈린다
  드래곤테일      26.7%    27%      25%      29%

  성격            전체     AS형     CS형     내구형
  고집            21.0%    30%      9%       23%
  겁쟁이          19.8%    3%       43%      17%   ← CS형 쪽

  도구            전체     AS형     CS형     내구형
  구애스카프      19.0%    22%      20%      10%
  자뭉열매        12.1%    10%      10%      23%   ← 내구형 쪽
```

형태 이름은 **AS형 · CS형 · 내구형** 처럼 사람이 쓰는 표기 그대로다.
처음엔 공격/특공만 봤는데, 도구 경향을 재 보니 **제일 센 축이 내구 ↔ 스피드**라
스피드를 축에 넣었다.

> 드래곤테일이 안 갈리는 것은 일부러다. **위력 60짜리를 데미지 때문에 드는 게
> 아니라 강제 교체 때문에 든다.** 물리기라는 이유로 물리형에 몰아 주면
> 실제와 거꾸로 나온다. 설명문에 강제 교체가 적힌 기술은 형태로 안 가른다.

**진짜 수확은 관찰이다.** 형태별 확률이 생기면 베이즈를 거꾸로 쓸 수 있다.

```
python forms.py 한카리아스 --봤다 용성군

  형태 비중   물리형 23%   특수형 59%   내구형 18%
  (본 것 없을 때: 물리형 47%  특수형 36%  내구형 17%)

  지진            67.0%  ->  56.8%   ↓
  화염방사        27.3%  ->  35.4%   ↑
  역린            25.7%  ->  18.0%   ↓
```

전에는 **본 기술 하나만 100%가 되고 나머지는 그대로**였다. 이제는 하나를 보면
안 본 기술 일곱 개의 확률이 같이 움직인다. 상위 30마리 중 **8마리가 형태로
뚜렷하게 갈린다** (5마리는 형태가 하나뿐이라 원래 갈릴 것이 없다).

> **상대의 노력치 배분은 대전 시작 때 공개되지 않는다.** 그래서 형태는 아는 값이
> 아니라 **끝까지 추론 대상**이다. 본 것이 없으면 원래 채용률 그대로 나오고,
> 볼수록 좁혀진다. 스피드 관찰로 몸이 걸러지면 형태도 같이 걸러진다.

### 성격과 도구는 근거가 다르다

셋을 같은 방법으로 붙이지 않았다. **근거의 등급이 다르기 때문이다.**

| | 무엇이 방향을 정하나 | 등급 |
|---|---|---|
| 기술 ↔ 형태 | "물리기는 공격으로 때린다" | **게임 규칙** |
| 성격 ↔ 형태 | "자기가 때리는 능력치를 깎는 성격은 안 쓴다" | **게임 규칙** |
| 도구 ↔ 형태 | 263마리로 잰 포켓몬끼리의 상관 | **측정한 경향** |
| 메가스톤 ↔ 형태 | 메가 폼의 종족값 | **게임 데이터** |

도구만 규칙이 없다. 챔피언스에는 공격/특공을 확정 짓는 도구가 힘의머리띠·박식안경
둘뿐이고 상위 20마리 채용률이 **0.0%** 다 (구애머리띠·구애안경·돌격조끼는 아예 없다).
그래서 **감으로 정하지 않고 데이터에서 쟀다.**

```
먹다남은음식  내구형 +0.69   스피드 -0.59
울퉁불퉁멧    내구형 +0.62   스피드 -0.54
구애스카프    스피드 +0.58   내구형 -0.41
생명의구슬    내구형 -0.43   물리형 +0.28
풍선         내구형 +0.03   ← 아무 경향 없음
```

마지막 줄이 중요하다. 이 측정은 **아무거나 다 맞다고 해 주지 않는다.**

> ! 한계를 분명히 해 둔다. 이건 **포켓몬끼리의 상관**이지 한 포켓몬 안의 상관이
> 아니다. "내구형 포켓몬이 먹다남은음식을 쓴다" 는 잰 것이고, "이 한카리아스가
> HB 배분일 때 먹다남은음식을 쓴다" 는 가정이다. 다만 방향은 데이터가 정했고,
> 세기는 `CONFIG` 에 두고 감도를 잰다.

메가스톤만 다르게 다룬다. 메가스톤은 **한 포켓몬만 쓰므로 포켓몬끼리 비교가
불가능**하다. 대신 메가 폼의 종족값이 있다 — 메가리자몽Y는 공격104 특공159 다.
임계값을 두지 않고 **차이를 증거의 세기로** 쓴다. 그래서 한카리아스나이트Z
(130/141, 차이 11) 는 저절로 거의 안 움직인다.

### 한 번 잘못 내렸다가 되돌렸다 — 고원의 최댓값은 잡음이다

메가 세기를 표본 1,291마리에서 재니 0.75 가 나와서 그리로 내렸다. 그때
**곡선이 평평하다는 것을 측정해서 알고 있었는데도**(0.75 와 1.125 가 0.054
차이) 최댓값을 따라갔다. 표본을 2,896마리로 늘리고 다시 재니:

```
0.375  차이 12.3        1.500  차이  0.000  ← 최고
0.750  차이  6.2        2.000  차이  0.043
1.125  차이  2.1        3.000  차이  8.7
```

**0.75 는 이제 6.2 만큼 나쁘다.** 내 원래 감 1.5 가 맞았다.

그래서 `--맞추기` 가 argmax 만 찍지 않고 **구별 안 되는 범위**를 같이 찍는다
(가능도가 최고에서 1.92 안 — 모수 하나 우도비 검정의 95% 문턱). 지금 값이
그 안에 있으면 **'구별 안 됨 — 그대로 둘 것'** 이라고 알린다.

```
가정값                  지금    최고    구별 안 되는 범위   표본
form_mismatch           0.05    0.05    0.05 ~ 0.05         3001   구별 안 됨 — 그대로 둘 것
nature_mismatch         0.003   0.003   0.001 ~ 0.005       3047   구별 안 됨 — 그대로 둘 것
mega_stat_strength      1.50    1.50    1.50 ~ 1.50         2896   구별 안 됨 — 그대로 둘 것
```

```

```

표본 3,936마리로 값을 확정한 뒤 다시 쟀다.

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 흔들림 |
|---|---|---|
| **기술을 형태로 안 가른다 (1-A 이전)** | **1 / 4** | **10.7%p** |
| 성격↔형태를 내 감(0.05)으로 되돌림 | 0 / 4 | 8.7%p |
| 성격을 형태로 안 가른다 | 0 / 4 | 8.0%p |
| 도구 경향을 안 쓴다 | 0 / 4 | 5.3%p |
| 메가 종족값을 안 쓴다 | 0 / 4 | 4.7%p |
| 메가 세기를 0.75 로 (한때 잘못 내렸던 값) | 0 / 4 | 3.3%p |
| 기술↔형태를 내 감(0.15)으로 되돌림 | 0 / 4 | 2.7%p |

읽는 법.

- **추천을 바꾸는 것은 "1-A 를 아예 끄기" 하나뿐이다.** 값을 어떻게 흔들어도
  추천이 그대로다. 세기를 표본으로 확정하면서 "뭘 누를까" 의 답이
  가정값에 매달리지 않게 됐다.
- **한때 잘못 내렸던 0.75 도 추천은 안 바꿨다** (승률 3.3%p). 그래도 틀린
  값이었고, 그걸 잡아낸 것은 표본을 늘려 곡선을 다시 그린 것이다.

`fetch_champs.py` 를 **집 회선에서** 돌리면 된다.

> 그 결과물(`data/usage_single.json`)과 일본어 이름표(`data/names_ja.json`)는
> 이미 저장소에 들어 있다. 외부 라이브러리도 안 쓴다 — 파이썬 3 만 있으면 된다.
> (`raw/` 만 빠져 있는데 그건 `build_data.py` 가 언제든 다시 받는 캐시다.)

python fetch_champs.py --받기                # 받아서 data/samples.json 에 넣는다
python samples.py                            # 못 알아들은 이름을 다 찍어 준다
python samples.py --맞추기
```

**HTML 구조를 못 봐서 파싱만 비어 있다.** 나머지는 다 돼 있다 — 주소 모으기,
일본어→한국어 잇기, 중복 거르기, 요청 간격, 중간 저장, 게시일 채우기,
`"source": "champs"` 붙이기, `samples.json` 형식 맞추기.

`--구조` 를 돌리면 **무엇을 어떻게 파싱해야 하는지 찍어 준다** — data-* 속성,
표, 페이지에 박힌 JSON, 본문에 보이는 포켓몬 이름, 그리고 첫 포켓몬 이름
**주변 HTML 을 그대로**. 그걸 보고 `STRATEGIES` 에 전략 하나만 채우면 된다.

흔한 두 형태(`data-*` 속성, 표)는 미리 넣어 뒀으니 그대로 될 수도 있다.
받아 온 뒤의 부분은 **네트워크 없이 검증해 뒀다** (검증 [34]번).



`champs.pokedb.tokyo` 는 **클라우드 IP를 통째로 막는다** (robots.txt 까지 403).
그래서 이 저장소가 도는 환경에서는 못 읽는다. 집 회선에서 돌리는 Claude Code 로
받아서 아래 형식으로 넣으면 된다. **`"source": "champs"` 를 꼭 넣을 것** —
그게 있어야 3배로 본다.

```json
{"parties": [
  {"source": "champs",
   "url": "https://champs.pokedb.tokyo/article/...",
   "season": 6, "rule": "M-6", "rank": 12,
   "publishedAt": "2026-09-10T12:00:00Z",
   "title": "기사 제목",
   "members": [
     {"name": "ガブリアス", "item": "オボンのみ", "ability": "さめはだ",
      "nature": "いじっぱり",
      "evs": {"H": 32, "B": 22, "D": 7, "S": 5},
      "moves": ["じしん", "ドラゴンテール", "ステルスロック", "つるぎのまい"]}
   ]}
]}
```

- 이름은 **일본어 그대로** 넣으면 된다. 한국어도 받는다.
- 노력치는 챔피언스 표기 (한 칸 최대 32, 합계 66). `"A32 S32"` 문자열도 받는다.
- 기존 `data/samples.json` 의 `parties` 배열에 **이어 붙이면** 된다.
  `url` 이 같으면 중복으로 보고 건너뛴다.
- 못 알아들은 이름은 조용히 버리지 않고 보고하므로, 넣고 나서
  `python samples.py` 로 확인하면 된다.

### 동반 출현 — champs 카드가 처음 값을 하는 자리

```
python samples.py --동반                    # 어느 쌍이 같이 다니나
python samples.py --동반 패리퍼             # 패리퍼가 보인다. 나머지는?
python samples.py --동반 --이후 2026-09     # 최근 메타만
python samples.py --동반 --룰 M-6
```

champs 카드에는 **기술도 배분도 없다** (기사 본문은 배분을 이미지로 올린다).
그래서 `--맞추기` 와 `--쌍` 에는 한 마리도 기여를 못 한다. 그런데 **명단은
온전하다.** 그 792마리가 여기서 처음 값을 한다.

```
포켓몬 A       포켓몬 B       같이   기대   리프트
대짱이         패리퍼          32     1.6    19.92   ← 같이 든다   (비 팀)
메타그로스     삼삼드래        36    11.1     3.19   ← 같이 든다
아머까오       팬텀            61    20.6     2.97   ← 같이 든다
하마돈         한카리아스      62    90.8     0.69   ← 서로 안 든다 (자리 경쟁)
브리두라스     아머까오        21    42.4     0.50   ← 서로 안 든다
```

리프트가 1보다 크면 **같은 파티에 들어가고**, 작으면 **같은 자리를 경쟁한다.**
**사용률로는 원리상 못 얻는다** — 사용률은 포켓몬마다 몇 %가 쓰는지만 주고
둘이 같은 파티인지는 안 준다.

쓸 곳은 **6마리 중 3마리 선출**이다. 선출 화면에서 상대 6마리를 다 보고도
"어느 셋이 나올까" 가 남는데, 이게 그 재료다.

```
python samples.py --동반 패리퍼

  같이 있을 놈    이 파티에서  평소    몇 배
  대짱이          98%          5%      19.9배   ← 거의 같이 온다
  브리두라스      84%         31%       2.7배   ← 거의 같이 온다
  메타그로스      56%         13%       4.3배   ← 거의 같이 온다
  한카리아스      56%         62%       0.9배
```

> 마지막 줄을 읽는 법. 한카리아스는 **아무 파티에나 62%** 들어 있어서,
> 같이 나올 확률 56%는 **평소보다 낮은** 것이다. 확률만 보고 "같이 온다" 로
> 읽으면 거꾸로 된다. 그래서 표시는 **확률이 높고 평소보다도 높을 때**만 붙인다.

> ! **이 표만은 메타에 매인다.** 세기(`--맞추기`)는 "특수형은 특공 깎는 성격을
> 안 쓴다" 처럼 사람의 습성이라 시즌이 바뀌어도 그대로인데, 어느 조합이
> 세냐는 룰이 바뀌면 바뀐다. `--이후` 나 `--룰` 로 좁혀서 볼 것.

### 두 가지를 섞지 않는다

- **시즌.** 시즌이 바뀌면 메타가 바뀐다. 시즌을 반드시 같이 받고 나눠서 본다.
- **랭커 편향.** 구축기사는 잘 나가는 구성 쪽으로 치우쳐 있다.
  그래서 표본으로 **마진을 갈아치우지 않는다.** 마진은 사용률 것을 그대로 쓰고,
  표본은 **조합만** 고치는 데 쓴다.

## 기술 구성 갈래 (1-C)

```
python combos.py 한카리아스
python combos.py 한카리아스 --봤다 스텔스록
python combos.py                       # 갈래를 찾을 수 있는 포켓몬 목록
```

표본으로 두 가지를 고친다.

### 고친 것 1 — 사용률 목록 밖의 기술

사용률 자료에는 포켓몬마다 **기술 상위 10개**만 있다. 표본을 세 보니
한카리아스가 실제로 쓴 기술 456회 중 **목록 안이 323회(71%)** 뿐이었다.

```
목록 밖인데 많이 쓰인 것: 칼춤 25 · 압정뿌리기 22 · 불꽃엄니 17 · 독찌르기 15
```

즉 **칼춤 한카리아스는 모델에서 확률이 0 이었다.** 나올 수가 없었다.

확률을 얼마나 줘야 하는지는 **사용률이 답을 알고 있다.** 상위 10개의 채용률
합이 298%이고 기술칸은 4개(400%)다. 차이인 **102%가 목록 밖 기술들의 몫**이다.
얼마인지는 사용률이 알려 주고, **누구에게 줄지는 표본이 알려 준다.**

> 표본의 목록 밖 비율 117% vs 사용률이 남긴 예산 102% — 15% 안에서 맞는다.
> 랭커 쪽이 조금 더 많이 쓰는 셈이다.

### 고친 것 2 — 기술끼리의 조합

쌍을 하나하나 넣는 대신 **갈래**로 본다. 실제 구성이 뭉쳐 있기 때문이다.
표본에서 갈래를 찾고(베르누이 혼합·EM), 갈래 개수는 BIC 로 고른다.

```
한카리아스 — 표본 114마리 · 갈래 3개
  1번 (54%)  역린 + 화염방사 + 칼춤
  2번 ( 7%)  파워젬 + 대지의힘 + 용성군
  3번 (39%)  스텔스록 + 드래곤테일 + 압정뿌리기

  기술          출처   전체    1번   2번    3번
  지진          사용률 67.0%   76%   0%     67%
  스텔스록      사용률 39.6%    5%   0%     94%   ← 갈래로 갈린다
  드래곤테일    사용률 26.7%    0%   0%     68%   ← 갈래로 갈린다
  역린          사용률 25.7%   48%   0%      0%   ← 갈래로 갈린다
  칼춤          표본   21.3%   37%   0%      3%   ← 갈래로 갈린다
  압정뿌리기    표본   18.8%    2%   0%     45%   ← 갈래로 갈린다
```

### 형태와 갈래를 곱해서 하나로

갈래만 쓰면 1-A 를 **대체**해 버린다. 1번 갈래에 역린과 화염방사가 같이
들어 있어서, 역린을 봐도 "1번"까지만 알고 AS/CS 구분이 흐려진다. 실제로
그렇게 짰다가 **역린을 봤는데 CS형이 4%에서 33%로 올라갔다** — 1-A 가 더
맞았던 것이다.

둘은 **서로 다른 것을 아는 신호**다.

| | 무엇을 아나 | 믿을 근거 |
|---|---|---|
| 1-A | 물리기는 공격으로 때린다 | 게임 규칙 — 표본 수와 무관 |
| 1-C | 실제 구성은 몇 갈래로 뭉친다 | 표본에서만 알 수 있다 |

그래서 대체하지 않고 **승산에서 곱한다.** 칸을 (형태 × 갈래)로 펴고,
섞으면 사용률 채용률이 나오도록 한 번에 맞춘다.

```
AS형  -> 1번 68%  2번  0%  3번 31%
CS형  -> 1번  3%  2번 95%  3번  2%
내구형 -> 1번  5%  2번  2%  3번 93%
```

**맞추는 마진은 두 개뿐이다 — 노력치(사용률)와 기술(사용률).**
갈래 비중에는 맞출 마진이 없다. 갈래는 관측값이 아니라 표본에서 찾아낸
잠재 변수다. 처음에 "섞으면 갈래 비중이 나오도록" 맞췄더니 1번 비중 54%가
AS형 47%보다 커서 **남는 몫이 CS형으로 밀렸고**, 특수형인데 역린·칼춤을 든
한카리아스가 나왔다.

### 결과 — 본 것 하나가 훨씬 많이 말해 준다

| 본 것 | 1-A 만 | 1-A × 1-C |
|---|---|---|
| 스텔스록 | 내구형 19% | 내구형 **38%** |
| 드래곤테일 + 스텔스록 | 내구형 22% | 내구형 **53%** |
| 역린 | AS형 84% | AS형 **95%** |
| 용성군 | CS형 69% | CS형 **99%** |
| 칼춤 | *보이지도 않음* | AS형 **82%** |

뽑아 보면 구성이 일관된다.

```
AS형   고집     지진 역린 칼춤 스케일샷
CS형   겁쟁이   용성군 화염방사 파워젬 스텔스록
내구형 장난꾸러기 스텔스록 지진 드래곤테일 압정뿌리기
```

지금 **39종**에 갈래 모델이 붙어 있다 (표본 25마리 이상). 전체 파이프라인
재현 오차는 0.5~1.3%p 로 표본 잡음 수준이다. 표본이 늘면 저절로 늘어난다.

## 도구와 기믹 (턴 루프)

> 이 절은 **사용자가 테스트로 잡아낸 결함**에서 시작됐다.
> 아머까오로 한카리아스를 400판 상대해 놓고 "아머까오가 진다" 고 보고했는데,
> *"철벽만으로도 아머까오가 이길 것 같은데 제대로 한 거 맞아?"* 라는 되물음에
> 확인해 보니 **아머까오의 도구 1·2·3위가 전부 미구현**이었다
> (울퉁불퉁멧 66% · 먹다남은음식 24% · 자뭉열매 9%, 합쳐서 99%).
> 맨몸으로 싸우고 있었다. 접촉기를 네 번 맞고도 울퉁불퉁멧 반동이
> 한 번도 안 들어갔다.

### 도구 — 설명문에서 읽는다

`battle.item_behaviors` 가 도구 설명문을 규칙으로 읽는다. 데미지 도구와 같은
방식이라 새 도구가 나와도 따라온다. **166개 전부 읽힌다.**

턴 루프에 실제로 붙은 것 —

| 무엇 | 도구 |
|---|---|
| 버티기 | 기합의띠, 기합의머리띠 |
| 회복 | 먹다남은음식(턴마다), 자뭉열매·오랭열매(반피에서) |
| 상태 회복 | 리샘·유루·버치·복슝·복분·배리·시몬열매, 멘탈허브 |
| 접촉 반동 | 울퉁불퉁멧 |
| 타입 무효 | 풍선 (맞으면 터진다) |
| 랭크 복구 | 하양허브 |
| 필드 시드 | 사이코시드·그래스시드·일렉트릭시드·미스트시드 |
| 날씨·필드·스크린 연장 | 빛의점토, 축축한바위, 뜨거운바위, 보송보송바위, 차가운바위, 그라운드코트 |
| 위력 | 노말주얼 |
| 명중·회피 | 광각렌즈, 반짝가루, 포커스렌즈 |
| 급소업 | 초점렌즈, 대파 |
| 교체 강제 | 레드카드, 탈출버튼 |
| 그 밖 | 조개껍질방울(흡수), 왕의징표석(풀죽음) |

**아직 안 붙은 것도 숨기지 않는다.** `battle.APPLIED_ITEM_KINDS` 밖에 있는 것들이다 —
`quick`(선제공격손톱) · `drain_boost`(큰뿌리) · `pp`(과사열매) · `bind_chip`(조임밴드) ·
`metronome` · `only_for`(전기구슬) · `free_switch`(아름다운허물).
전부 **모델에 그 개념 자체가 없는** 것들이고, 그런 도구를 들고 싸우면 대전이 경고를 띄운다.

> ### 승률 옆에 경고가 찍혀 있으면 그 숫자를 그대로 믿지 마라.

### 기믹

- **스크린** — 리플렉터(물리만), 빛의장막(특수만), 오로라베일(둘 다). 급소에는 안 통한다.
  빛의점토가 3턴 늘려 준다.
- **날씨 타입 배율** — 비: 물 1.5 / 불꽃 0.5, 쾌청: 불꽃 1.5 / 물 0.5.
  하마돈 모래날림 99.8%, 고릴타 그래스메이커 99.8% 라 날씨는 나오기만 하면 깔린다.
- **대타출동 · 희망사항 · 치유소원 · 아픔나누기 · 흑안개 · 버티기 · 길동무 ·
  멸망의노래 · 배턴터치 · 트릭 · 회생의기도 · 안개제거 · 기충전 · 물붓기 · 배북**

상위 60종이 실제로 쓰는 변화기 중 **못 읽은 것의 사용률 무게가 591 에서 4 로** 줄었다.

> 희망사항과 치유소원은 `Side` 가 아니라 `Party` 에 건다. **자리에 걸리는 것**이라
> 건 놈이 빠져도 다음에 나온 놈이 받는 게 이 기술의 핵심이기 때문이다.

### 게임 데이터에 숫자가 없는 것들

기술 설명문이 "같은 편 필드를 리플렉터 상태로 만든다" 까지만 적고 **수치를 안 준다.**
압정과 같은 방식으로 본편 값을 `calc.CONFIG` 에 모으고 대전이 "미확인 값" 경고를 띄운다.

| 값 | 쓰는 값 |
|---|---|
| 스크린 감소율 | 1/2 |
| 날씨 타입 강화 / 약화 | 1.5배 / 0.5배 |
| 필드 타입 강화 | 1.3배 |
| 모래바람 칩댐 | 1/16 |
| 압정 수치 | 스텔스록 1/8 x 바위 상성, 압정 1/8~1/4 |

**실전에서 계산이 어긋나면 여기부터 의심한다.**

## 7단계 — 이번 턴에 무엇을 둘까 (`search.py`)

```
python search.py 한카리아스,아머까오,누리레느 하마돈 --초 10 \
       --기술 지진,역린,화염방사,칼춤 --봤다 자뭉열매
```

4-B(`battle.py`)는 **내가 수순을 미리 정해 주면** 그대로 돌려 본다.
여기는 반대다 — **이번 턴에 둘 수 있는 모든 수(기술 + 교체)를 각각
판이 끝날 때까지 돌려 보고 제일 나은 것을 고른다.**

상대 몸은 매 판 사용률대로 새로 뽑는다(4-C). 본 기술·본 도구가 있으면 그만큼 좁혀진다.

### 얼마나 깊이 보나 — 되도록 끝까지

기본은 **끝까지**다. 예산(`--초`)이 모자랄 때만 이 순서로 줄인다.

1. **판수를 줄인다** (깊이는 그대로)
2. **가망 없는 수를 먼저 접는다.** 적은 판수로 한 바퀴 돌려 하위 절반을
   떨어뜨리고, 살아남은 수에 판수를 두 배로 준다. 되풀이하면 마지막에
   후보 한둘이 제일 많은 판수를 받는다.
3. **그래도 모자라면** 그때만 6턴에서 끊고 판세로 점수를 매긴다.
   썼으면 보고서에 적는다.

### 보고서는 확실하지 않으면 그렇다고 말한다

```
  수                       승률      판수       오차
  아머까오 로 교체          99.4%      982   ± 1.6%p
  용성군                 94.9%       90   ± 5.3%p  (일찍 접음 — 덜 믿을 것)
  화염방사                94.1%      981   ± 1.6%p
  ...
  => 아머까오 로 교체  (승률 99.4% ±1.6%p, 982판)
  ! 오차 범위가 겹치는 수가 있다 — 확실하지 않다
```

일찍 접은 후보도 버리지 않고 남긴다. 나중에 지고 나서
"왜 그 수는 안 봤나" 를 되짚을 수 있어야 하기 때문이다.

### 답이 명백한 상황으로 시험해서 결함 둘을 잡았다

**(가) `Policy` 가 내 기술을 몰래 바꿔 썼다.** 계획은 첫 턴 한 수뿐인데 그 뒤부터
사용률 상위 기술을 꺼내 썼다. **땅 기술만 든 한카리아스가 2턴째부터 화염방사를
쓰면서 아머까오(비행 — 땅 무효)를 96.7% 로 이기고 있었다.** 숫자가 그럴듯해서
눈으로는 절대 못 잡는다.
고치다 또 하나 나왔다 — 계획이 끝나면 **첫 수를 끝까지 반복**하고 있었다.
"칼춤을 두면 어떻게 되나" 가 아니라 "여섯 턴 내리 칼춤만 두면" 을 재고 있었던 것이다.

**(나) 점수가 "이기면 1.0" 이었다.** 3마리 다 살려 이긴 것과 두 마리 내주고 간신히
이긴 것이 같은 점수라, **"이놈을 공짜로 잃어도 어차피 벤치가 이기니 괜찮다"** 는
수를 골랐다. 이김 안에서 남은 파티 HP 로 가르게 했다
(이김 0.70~1.00 / 비김 0.35~0.50 / 짐 0.0).

고치고 나니 같은 자리에서 답이 뒤집힌다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1등 | 스텔스록 96.2% | **누리레느 로 교체 86.2** |
| 2등 | 누리레느 교체 91.5% | 스텔스록 78.2 |

> 시험을 만드는 데도 두 번 미끄러졌다. "땅 기술만 줬다" 면서 스톤에지·드래곤테일을
> 끼워 넣어 시험이 무의미했고, 벤치가 뒤처리를 해 주는 바람에 "무조건 빼야 하는
> 자리" 가 아니었다. 벤치를 빼고 **정말로 때릴 수단이 없게** 만들어야
> 0% 대 100% 로 갈렸다.

## 어떤 값을 먼저 확인해야 하나

```
python sensitivity.py
```

`calc.py` 의 `CONFIG` 에는 챔피언스에서 확인한 적 없는 값이 스무 개 넘게 있다
(전부 본편 값 가정). 다 실측할 수는 없으니, **하나씩 흔들어 보고 답이 바뀌는 것만**
골라낸다.

처음 재 봤을 때 답을 흔든 것은 **자속(53.3%p)과 급소 배율(1/5 대면에서 추천이
바뀜)** 둘뿐이었다. 그 둘은 그 뒤 **사용자가 1.5배로 확정해 줬다.**
**화상 물리 반감(0.5)과 마비 스피드(0.5)도 사용자가 확정해 줬다** (2026-09-18).
그래서 지금 남은 것은 미확인 값 14개이고, 접전·조건이 걸리는 대면 8개로 다시 재면 이렇다.

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 최대 흔들림 |
|---|---|---|
| **모래 칩 1/16 → 1/8 (2세대)** | **1 / 8** | 0.8%p |
| 나머지 13개 | 0 / 8 | 0.0%p |

> **남은 14개 중 답을 흔드는 것은 모래 칩댐 하나뿐이고, 그것도 0.8%p 다.**
> 즉 **"뭘 누를까" 의 답은 지금 믿어도 된다.**

단, 0.0%p 를 "안 중요하다" 로 읽으면 안 된다. **이 8개 대면에서 그 조건이 아예
안 나왔다** 는 뜻일 수도 있어서, 조건을 깨우는 대면을 따로 넣어 다시 재야 한다.

### 형태 가정값은 따로 잰다

```
python sensitivity.py --형태
```

1-A 가 쓰는 `form_mismatch` 는 위 표에 못 넣는다. 위 표는 **상대를 하나로 고정해
놓고** 재는데, 형태는 상대를 분포로 뽑을 때만 작동하기 때문이다. 따로 쟀다.

| 바꿔 본 값 | 추천이 바뀐 대면 | 승률 최대 흔들림 |
|---|---|---|
| 기술↔형태를 더 믿는다 0.15 → 0.05 | 1 / 4 | 4.0%p |
| 기술↔형태를 덜 믿는다 0.15 → 0.40 | 1 / 4 | 6.0%p |
| **기술을 형태로 안 가른다 (1-A 이전)** | **1 / 4** | **11.3%p** |
| 성격↔형태를 덜 믿는다 0.05 → 0.20 | 1 / 4 | 4.0%p |
| 성격을 형태로 안 가른다 | 1 / 4 | 4.7%p |
| 도구 경향을 두 배로 믿는다 1.0 → 2.0 | 0 / 4 | 0.7%p |
| 도구 경향을 안 쓴다 | 0 / 4 | 2.0%p |
| 메가 종족값을 두 배로 믿는다 1.5 → 3.0 | 1 / 4 | 2.7%p |
| 메가 종족값을 안 쓴다 | 0 / 4 | 2.7%p |

읽는 법.

- **1-A 는 장식이 아니다.** 기술을 안 가르던 때로 되돌리면 승률이 11.3%p 움직이고
  4개 중 1개에서 추천이 바뀐다. 넷 중 제일 큰 것이 이것이다.
- **도구 경향은 넷 중 제일 약하다** — 추천은 하나도 안 바뀌고 승률 2.0%p 다.
  넣어서 손해는 없지만, 이것부터 정교하게 다듬을 이유는 없다.
- **확인 안 되는 가정값이 넷으로 늘었다.** 그중 셋이 4개 중 1개를 뒤집는다.

기술↔형태와 성격↔형태는 방향이 게임 규칙이라 확실하지만 **세기는 확인이 안 된다** —
사용률에 조합 정보가 없기 때문이다. 세기까지 확인하려면 형태와 기술이 같이 적힌
표본, 즉 **구축기사 샘플**이 필요하다 (1-B). 그게 1-B 를 해야 할 구체적인 이유다.

- **무효화 특성** — 부유, 천정부지, 축전, 피뢰침, 저수, 건조피부, 초식, 그리고 이를 뚫는 배짱
- 도구 — 생명의구슬, 힘의머리띠, 박식안경, 달인의띠, 타입 강화 도구, 반감 열매
  (타입 강화 도구와 반감 열매는 게임 설명문에서 자동으로 읽어내므로 새 도구가 나와도 따라온다)

특성은 데미지 관련 110개 중 **42개가 계산에 반영**돼 있고, 17개는 반영은 안 되지만
경고로 알려준다. 「베는 기술」「펀치 기술」 같은 분류는 게임 원본 데이터에서 뽑아냈다
(`moves.json` 의 `tags`).

**아직 못 함**

- 여러 번 때리는 기술, 위력이 변하는 기술 (공격기 335개 중 일부)
- 상태이상 입력은 화상만 (턴 루프에서는 전부 다룬다)

> 여기 "못 함" 은 **한 방 계산기(`calc.py`) 기준**이다. 날씨·필드·스크린·
> 탈·지구력·황금몸·미러아머·독치장·위기회피처럼 턴이 있어야 되는 것들은
> `battle.py` 의 턴 루프에서 처리한다 — 아래 "도구와 기믹" 참고.

못 하는 특성이 걸려 있으면 계산 결과에 `!` 경고가 뜬다.
`best.py` 는 여기에 더해 **위력 숫자를 믿으면 안 되는 기술 55개**도 `!` 로 표시한다.
자세한 점검 결과는 [docs/ai-design.md](docs/ai-design.md) 2장에 있다.

> 챔피언스에는 **구애하치마키·구애안경·돌격조끼가 없다.** 대신 힘의머리띠(물리 1.1배)와
> 박식안경(특수 1.1배)이 있다. 본편 감각으로 계산하면 틀리니 주의.

## 확인해 둔 게임 규칙

### 대전 형식

**6마리 파티에서 3마리를 선출한다.** 6대6이 아니다.

이것 때문에 대전이 시작되기 전에 이미 한 번 "서로의 6마리를 보고 동시에 3마리를 고르는"
결정이 일어난다. 조합은 `6C3 = 20` 이라 양쪽 합쳐 400가지 — 전부 훑어볼 수 있는 크기다.

3마리뿐이라 **교체할 여지가 적고**, 그래서 강제로 바꾸게 만드는 수(하품 · 날려버리기 ·
울부짖기)의 값어치가 크다. 거꾸로 스텔스록 같은 압정을 본편 6대6 감각으로 재면 과대평가가 된다.

> 사용률 데이터에는 `rank` 만 있고 **선출률이 없다.** 그 rank 가 파티 채용 기준인지
> 선출 기준인지도 아직 확인 못 했다. "상대로 만날 확률" 을 쓰려면 선출 기준이 맞다.

### 능력치 계산 (레벨 50)

챔피언스는 노력치 체계가 바뀌었다. **능력치당 최대 32, 총합 66.**
이 숫자는 "능력치에 그대로 더해지는 값"이다.

```
HP     = 종족값 + 75 + 노력치
그 외   = (종족값 + 20 + 노력치) × 성격보정        ← 소수점 버림
```

성격 보정은 1.1 / 1.0 / 0.9.

> 예전 노력치(0~252)와의 관계는 `예전 = 지금 × 8 − 4`.
> 종족값 1~255 × 노력치 0~32 조합 25,245가지를 기존 공식과 전부 대조해 확인했다.

### 데미지 비율 (레벨 50)

```
데미지 비율 = 22 × 기술위력 × 공격실능 ÷ 방어실능 ÷ 50 ÷ HP실능 × 난수
```

난수는 0.85 ~ 1.00 (16단계).

### 결정력 / 내구력

한 방에 죽는지를 숫자 하나로 비교하기 위한 지표.

```
결정력 = 공격실능 × 기술위력 × (자속·특성·상성·랭크 등 배율)
내구력 = HP실능 × 방어실능
```

| 조건 | 결과 |
|---|---|
| 결정력 ≥ 내구력 ÷ 0.374 | 확정 1타 |
| 결정력 ≈ 내구력 ÷ 0.407 | 약 50% |
| 결정력 < 내구력 ÷ 0.44 | 확정 2타 이상 |

0.44 = 22÷50, 0.374 = 0.44×0.85 로 정확히 떨어진다.
(나무위키에는 50% 지점이 0.411로 적혀 있는데, 실제로 계산하면 43.75%다. **0.407이 맞다.**)

### 성격 보정

성격 25개의 능력치 보정은 게임 내부 순번에서 나온다.
**올라가는 능력치 = 번호 ÷ 5의 몫, 내려가는 능력치 = 번호 ÷ 5의 나머지** (순서: 공격·방어·스피드·특공·특방).
몫과 나머지가 같으면 무보정(5종).

실제 사용률 데이터로 확인함: 1위 성격이 올려주는 능력치가 1위 노력치 배분과
일치하는 비율 90.1%, 성격이 깎는 능력치가 '안 쓰는 공격 능력치'인 경우 263마리 중 245마리.

### 아직 확인 못 한 것

실능 계산식과 개체값 체계는 **게임 화면과 대조해 확정됐다** (2026-09-17, 6/6 일치).
개체값은 없거나 전부 최대로 고정이다.

남은 것은 능력치 화면으로는 알 수 없고 **실제 대전의 숫자를 봐야** 하는 값들이다.

- 자속 보정 1.5배 / 급소 배율 1.5배 — 자속 기술 한 번, 급소 한 번이면 확정된다
- 화상 시 물리 반감 0.5배
- 마비 시 스피드 0.5배 — 이건 데미지가 아니라 순서로 확인한다

전부 `calc.py` 의 `CONFIG` 한 곳에 모여 있다. 자세한 것은
[docs/ai-design.md](docs/ai-design.md) 4장.
